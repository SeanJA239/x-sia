X-SIA 平台今天正式起步。这篇文章讲两件事:平台是什么,以及为什么这么搭技术栈。

## 平台是什么

一句话:把「你是谁」「你写了什么」「你能用什么」放进同一个账号里的社团平台。

具体来说是三件事的组合:

- **身份**——注册、现场核验、社员编号,这些构成了你在社团里"是谁"。
- **内容**——平台内发帖,或者给门面站的 `blog/` 目录提 PR,两条轨并存。
- **权益**——AI 对话额度、资源库下载,都是社费换来的、能实际感知到的东西。

这不是又一个校园论坛,也不是又一个网盘。过去这类工具往往各管一段——身份系统一套、内容系统一套、权益发放靠人工登记表——X-SIA 想做的是把三者接在同一个账号体系上。

社团内部工具起步,如果效果好,不排除给其他社团用。所以数据模型从第一天起就为多租户留了余地（所有业务表都带 `org_id`),但目前不做主题或部署层面的多租户——先把一个社团服务好。

## 技术栈,以及为什么

三个部署单元,一套身份:

| 单元 | 内容 | 技术 |
|---|---|---|
| 门面站 | 社团介绍、文章、活动回顾归档 | fumadocs + React Router,静态,部署在 Cloudflare Pages |
| 应用 | 发帖、成员主页、活动签到、资源、AI Chat | Expo(web 优先)+ Hono API |
| 数据 | 全部结构化数据与文件 | D1(SQLite)+ Drizzle;文件存 R2 |

**为什么门面站不用 Next.js。** 部署到 Cloudflare Workers 要经过 OpenNext 这层适配,而 Vite 系框架（React Router、TanStack Start 这类)可以直接上 Workers,没有这层转换开销。fumadocs 从 v16 起默认切到 Shiki 的 JS 正则引擎,也正是为了在 Workers 这类运行时里跑得起来。

**为什么内容要分流。** 编辑型内容——少数人写、走 git 提交、追求 SEO 和长期沉淀——放进 fumadocs;用户生成内容——多数人写、运行时产生、需要鉴权和审核——放进 D1。fumadocs 本质是构建时的文件系统模型,普通成员发一次帖不可能触发一次网站重新构建,所以从一开始就没打算让它承载 UGC。

**为什么用 Hono 而不是把 AI 网关单独部署。** AI 网关只是 Hono 里的一组路由。社团用一个 Cloudflare 账号,成员不接触 API Key,所有请求经网关代理、计量、限流。额度和计量数据同样落在 D1 里,不需要额外的服务。

**为什么是 Expo。** 应用需要覆盖网页和未来可能的原生场景,Expo 让这两者共享一套代码,web 优先意味着现在能立刻用,原生分发不是第一年的重点。

## 现在能用什么

第一年砍到这个范围:注册与现场核验、会员资格状态机（含社员编号分配)、成员个人页、AI 网关与「我的权益」页、资源共享、网页版会员卡,以及你现在正在看的门面站。

活动签到、论坛、称号授予的自助界面会在后续迭代跟进——不急着一次做全,但骨架（数据表结构)已经在第一版里留好了。

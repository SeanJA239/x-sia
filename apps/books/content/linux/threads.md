# 线程、同步与并发正确性

> 先修：进程、操作系统抽象与基础 C/Python 语法。目标：从共享状态的不变量出发理解互斥、条件变量、原子操作和死锁，能手工分析交错，并运行一个有界的线程计数示例。线程不是自动加速选项。

## 线程共享资源，也共享错误影响

一个进程内的线程通常共享地址空间、工作目录和文件描述符等资源，各自持有执行寄存器、栈和调度状态。一个线程越界写内存可能破坏其他线程的数据；把工作拆成线程并没有获得进程级地址隔离。

并发是多个执行流可以交错推进，并行是它们同时执行。单核也有并发错误，多核并行则使更多交错真实重叠。判断正确性时应考虑所有允许的顺序，而不是只解释一次运行结果。

## 从丢失更新到不变量

令共享计数器初始为 0，两线程都执行加一。一个允许的逻辑交错是 A 读 0、B 读 0、A 写 1、B 写 1。两个任务都完成，结果却是 1。

在 C/C++ 中，对普通共享对象进行未同步的冲突访问会构成数据竞争，语言语义可能是未定义行为；不能把上面的交错当成其所有实际后果。教学交错用于解释为什么需要同步，不是保证错误程序只会“少算一”。

### 临界区的边界由不变量决定

若银行转账要求两个账户总余额不变，就必须协调扣款和入账；分别保护两行赋值不一定足够。对队列，不变量可能包括头尾索引、有效元素数与槽位内容的一致关系。先写出状态转换前后必须成立的条件，再决定锁的范围。

锁过小可能漏掉关联状态，锁过大则限制并发，甚至把慢 I/O 纳入所有线程的等待路径。优化锁粒度之前，应先明确对象所有权和生命周期。

## 可运行例子：锁与结果收集

下面只使用 Python 标准库，创建两个线程，各做一千次计数；不访问网络或系统服务。

```python
# example: threads-counter
import threading

lock = threading.Lock()
state = {"count": 0}

def worker():
    for _ in range(1000):
        with lock:
            state["count"] += 1

threads = [threading.Thread(target=worker) for _ in range(2)]
for thread in threads:
    thread.start()
for thread in threads:
    thread.join()
assert state["count"] == 2000
print(state["count"])
```

`with lock` 保护整个读改写，并在作用域正常离开或抛异常时释放锁。`join()` 等待线程结束；仅创建线程对象或调用 start，不代表结果已经就绪。

不要根据某个 Python 实现中的 GIL 推出“我的业务状态无需锁”。解释器实现、版本、扩展模块和操作组成会影响行为；GIL 也不是业务事务锁。此例说明同步契约，不测量并行加速，移除锁后碰巧得到 2000 不证明无锁版本正确。

## 条件变量：等待谓词，而不是积攒通知

假设消费者需要等待队列非空。正确的概念结构为：持锁 → 在队列为空时等待 → 重新检查 → 取元素 → 解锁。等待操作把释放锁和进入等待的过程与通知协议正确衔接，并在返回前重新取得锁。

### 为什么用 while，而不是 if？

即使一次通知是因为队列加入了元素，另一个消费者也可能先取得它；某些接口还允许虚假唤醒。因此通知只表示“值得重新检查”，并不把一个元素永久分配给收到通知的线程。

生产者应先在相应同步下更新状态，再按协议通知。判断关闭也需要谓词：当队列为空且系统已关闭，消费者可以结束；仅有“队列暂时为空”不能推断生产已经结束。

## 原子操作、可见性与顺序

原子操作保护某个操作不被观察为中间状态，但一个原子计数器不自动把整个数据结构变成事务。多字段不变量仍可能需要锁或专门的无锁算法。

还要区分原子性与内存顺序。若生产者先写 payload，再发布 ready 标志，消费者需要在观察标志与读取 payload 之间建立相应同步关系。语言的 acquire/release 等规则用于表达这种关系；不能用“处理器通常按顺序执行”代替语言内存模型。

`volatile` 一般不能替代线程同步原语；其用途与保证随语言和上下文不同。内核代码还可能使用专门的访问与屏障机制，也不能直接把某段内核写法复制成可移植 C++ 程序。

### 伪共享为什么会拖慢独立计数？

两个线程可能修改逻辑上独立、却位于同一缓存行的字段，引发缓存一致性流量。此时没有同一个计数器的数据竞争，性能仍会下降。是否需要对齐、填充或局部累加，应根据实际布局和测量判断，不能靠给所有结构体盲目增加填充。

## 死锁、饥饿与活锁

死锁的一组经典必要条件包括互斥、占有并等待、不可强制剥夺和循环等待。A 持有锁 L1 等 L2，B 持有 L2 等 L1，就是最小的循环示例。

给锁定义统一获取顺序可以破坏循环等待，但要保证所有调用路径遵守，包括错误清理和回调。超时让任务有机会退出等待，不自动回滚已修改的状态。饥饿是某个任务长期无法获得资源；活锁则可能大家都在重试和退让，却没有完成有效工作。

## 性能算例：增加线程的上限

若一项工作有串行比例 $s$，其余部分可理想并行，在 $p$ 个处理单元上的模型加速比为：

$$
S(p)=\frac{1}{s+(1-s)/p}.
$$

取 $s=0.2,p=4$，得 2.5 倍，而不是 4 倍；即使无限增加处理单元，上限仍为 5 倍。实际锁竞争、线程管理、内存带宽和任务不均衡会继续降低收益。这是固定工作量模型，不是所有扩展场景的定律。

## 练习与解题提示

1. 单核是否可以发生丢失更新？
2. 为什么把 count 声明为 volatile 不等于获得互斥？
3. 条件变量通知后，消费者为什么还要检查队列？
4. 写出双锁死锁环，并给出一个统一锁序。
5. 当 $s=0.1,p=8$ 时，理想加速比是多少？

**答案：** 1. 可以，切换能发生在读改写之间。2. 它不提供所需的线程原子性和同步协议。3. 通知不是资源所有权，状态可能已经再次变化。4. A 持 L1 等 L2、B 持 L2 等 L1；要求全部路径先 L1 后 L2。5. $1/(0.1+0.9/8)\approx4.706$，忽略附加开销。

## 小结与参考

并发正确性先于线程数量。通过不变量定义临界区，通过所有权约束生命周期，通过同步关系定义可见性，再讨论性能。

- [OSTEP：Concurrency](https://pages.cs.wisc.edu/~remzi/OSTEP/)：线程、锁、条件变量、信号量与常见错误应配合阅读。
- [Python threading](https://docs.python.org/3/library/threading.html)：核对 Lock、Condition、Thread 的实际接口。
- [POSIX pthreads 概览](https://man7.org/linux/man-pages/man7/pthreads.7.html)：区分 POSIX 接口与某一种语言封装。
- [C++ Core Guidelines](https://isocpp.github.io/CppCoreGuidelines/CppCoreGuidelines)：选读 CP 并发规则，尤其是锁与数据的关联设计。

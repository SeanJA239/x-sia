# Shell、引用与数据流

> 先修：[文件、目录与权限模型](book:linux/files)。环境：Bash 5 与 GNU 工具；本章不是 POSIX sh 的通用语法清单。目标：准确预测程序收到的参数、描述符和退出状态，能写一个保留数据边界、显式处理失败的文本处理脚本。

## 3.1 Shell 的输出不只是屏幕文字

当你写 `grep ERROR app.log`，Shell 的工作不是把这串原文直接交给 grep。它先解析语法、展开相应内容，再构造程序名、参数数组、环境及重定向关系。grep 最后收到的参数可以理解为三个独立字符串：程序名、`ERROR`、`app.log`。

因此，可靠脚本的第一个问题不是“这条命令看起来对吗”，而是“程序最终收到几个参数，每个参数的字节边界在哪里”。变量内容含空格和 `*` 时，答案可能与肉眼直觉不同。

```bash
# example: shell-argv
name='annual report.txt'
show_args() {
  printf 'argc=%s\n' "$#"
  local item
  for item in "$@"; do
    printf '<%s>\n' "$item"
  done
}
show_args "$name"
show_args ""
show_args
```

预期三次参数个数分别为 1、1、0。第二次有一个空字符串参数，第三次根本没有参数，两者不等价。`"$@"` 把每个位置参数保留为独立元素；`"$*"` 则把它们连接成一个字符串，连接方式涉及 IFS 的首字符。

Shell 适合安排现有程序、连接数据流和处理退出状态。复杂的数据结构、类型规则和大型业务逻辑往往更适合 Python 或其他通用语言。决定使用 Shell，不等于必须把所有事情压缩成一个难以测试的管道。

## 3.2 展开顺序与引用规则

Bash 在不同上下文里按规则处理花括号展开、波浪线展开、参数展开、命令替换、算术展开、分词、路径名展开和引用移除。它们不是一个适用于所有语法位置的无条件流水线：普通命令参数、赋值、`[[ ... ]]` 和算术上下文各有规则。

![图 3-1：普通命令参数在展开中可能从一个表达式变成多个参数。双引号保留参数展开结果的边界，数组保留多个已有边界；图示不是所有 Bash 上下文的完整语法。](asset:linux-expansion)

| 写法 | 主要含义 | 容易遗漏的边界 |
|---|---|---|
| `'literal $name'` | 保留字面文字 | 单引号内不能直接嵌入另一个单引号 |
| `"$name"` | 展开变量并保留一个参数 | 不是停止所有展开，而是阻止通常的分词与通配符展开 |
| `$name` | 普通参数位置可能分词并展开路径名 | 空白、星号等可能改变参数数量 |
| `"${items[@]}"` | 每个数组元素保留为一个参数 | 空数组与一个空字符串元素不同 |
| `$(command)` | 捕获标准输出作为替换结果 | 删除末尾换行，不能当作任意二进制容器 |

假设 `name='report *.txt'`。不加引号的 `$name` 可能先按空白分成 `report` 和 `*.txt`，再把后者展开成当前目录里的匹配文件。结果因此不仅依赖变量，还依赖当前目录内容。默认没有匹配时，Bash 通常保留模式字面量；`nullglob` 或 `failglob` 会改变这一行为。

变量展开结果不会普遍被重新当作 Shell 语法执行。把分号放进普通变量，不等于自动产生第二条命令；但未经引用的展开依然会造成参数注入、选项误解与路径展开。`eval` 则会显式引入再次解析，使数据进入代码层，不应用它解决数组和引用问题。

### 用数组保存命令，而不是拼接命令字符串

```bash
# example: shell-array
args=(printf '%s\n' 'first file.txt' '' '*.txt')
"${args[@]}"
```

输出为一行 `first file.txt`、一行空行、一行字面 `*.txt`。这里数组表达的是参数结构，不需要把每个元素手工加一层引号后再 `eval`。

对支持的外部工具，可使用 `--` 标记选项结束。引用保留参数边界，`--` 阻止后续名字被当作选项，两者解决的问题不同。相对路径带上 `./` 也能让名字不以短横线开头，但应理解路径基准，不能把字符串改写当作所有接口的通用安全方案。

## 3.3 变量默认值、测试与条件分支

`${name:-fallback}` 在变量未设置或为空时取默认值；`${name-fallback}` 只在未设置时取默认值。配置中的“未提供”和“明确提供空值”可能有不同意义，不能随意互换这两种形式。

`[ ... ]` 是一个测试命令形式，需要用空格把操作数与运算符分开，普通参数展开规则仍然重要。Bash 的 `[[ ... ]]` 是条件语法，避免了其中许多普通分词问题，但还引入模式匹配等特定语义。

```bash
# example: shell-condition
value='report.txt'
if [[ "$value" == *.txt ]]; then
  printf 'suffix matched\n'
fi
if [[ "$value" == '*.txt' ]]; then
  printf 'unexpected literal match\n'
else
  printf 'literal did not match\n'
fi
```

第一次右边是模式，第二次右边被引用而成为字面字符串，结果不同。处理整数比较可用合适的算术或测试语法，但应先验证外部输入的格式和范围；不要把任意用户文本直接丢进算术求值器，再假设它只是普通十进制数字。

条件分支判断的基本对象是退出状态：0 为真，非零为假。`grep` 返回 1 通常表示没有匹配，不一定是故障；返回 2 一般表示错误。对这类命令，把所有非零值都归入“系统异常”会产生错误告警。

## 3.4 描述符与重定向：从左到右改变连接

文件描述符 0、1、2 通常表示标准输入、标准输出和标准错误。它们是进程内的引用，不是固定绑定键盘、屏幕、打印机的硬件编号。Shell 在运行命令前安排连接关系，程序通常不必知道自己面对的是终端、文件还是管道。

![图 3-2：管道默认连接上游 stdout 与下游 stdin；stderr 仍独立。重定向改变的是描述符当时的引用，复制不会建立永久跟随关系。](asset:linux-shell)

比较两种写法：

```bash
command > output.log 2>&1
command 2>&1 > output.log
```

第一行先把描述符 1 打开到文件，再复制当时的 1 到 2，所以两者进入文件。第二行先让 2 指向原来的 1，再改变 1，因此 2 仍指向旧目的地。

| 执行阶段 | 第一种写法的 fd 1 / fd 2 | 第二种写法的 fd 1 / fd 2 |
|---|---|---|
| 初始 | 终端 / 终端 | 终端 / 终端 |
| 第一项重定向后 | 文件 / 终端 | 终端 / 终端的复制引用 |
| 第二项重定向后 | 文件 / 文件 | 文件 / 原终端 |

`>` 会在程序读取输入前打开并截断目标。因此 `grep pattern data.txt > data.txt` 不是原地过滤技巧，而是可能先清空原始数据。要更新原文件，应使用独立临时文件、检查结果，再按预定发布协议替换。

重定向本身也会失败，例如父目录不存在。此时程序可能根本没有开始运行。看到输出文件为空，也不能立即断言程序处理了空输入；它可能在 Shell 建立输出文件后、真正运行之前失败。

### Here document 中的展开由结束标记的引用决定

```bash
# example: shell-heredoc
name=student
cat <<'TEXT'
$name is literal here.
TEXT
cat <<TEXT
Hello, $name.
TEXT
```

第一段输出字面 `$name`，第二段输出 `student`。生成配置和代码文件时，经常需要前一种形式，避免当前 Shell 抢先解释模板里的变量。这里的 `cat` 只向标准输出写入，没有改写系统文件。

## 3.5 管道、背压与数据边界

`producer | consumer` 通常使两端并发运行，并不要求把上游全部输出存完后才启动下游。管道是有界字节流：数据暂时不足时读者可能等待，容量不足时写者可能等待。这种背压使上游不能无限快地产生数据。

对各阶段记录大小和工作量相近的长期稳定流水线，若第 $i$ 阶段处理速率为 $r_i$，在忽略其他瓶颈的模型下：

$$
r_{\mathrm{pipeline}}\leq\min_i r_i.
$$

### 例题：加速读取为什么没有效果？

读取、解析和输出速度分别为 100、20、80 条每秒，稳态吞吐上限是 20 条每秒。把读取升级到 200 条每秒，只让上游更快填满缓冲，不改变解析瓶颈。若解析速度固定，上游比它多产生的速率为 $100-20=80$ 条每秒；一个能容纳 400 条同样大小记录的抽象缓冲，从空到满约需 5 秒。

这个 400 条缓冲只是教学模型，不是 Linux pipe 容量的承诺。真实管道按字节计，容量可能受系统配置和运行情况影响。第一条结果延迟与长期吞吐也不同：吞吐接近最慢阶段，不表示第一条结果只需经历最慢阶段。

管道不保存应用层记录边界。一次 write 不保证对应下游一次 read；消费者必须按协议恢复记录，例如按换行、固定长度或带长度前缀解析。小于等于 `PIPE_BUF` 的写入在相应条件下有不与其他写者交错的保证，但这不等于读调用自动返回同样大小的消息。

消费者提前关闭时，上游继续写入可能收到 SIGPIPE，或在相关信号处理条件下得到 EPIPE。`yes | head -n 1` 中，下游只要一行就退出，上游被终止可能是预期的控制流程，而不是要保留一个永远运行的生产者。

## 3.6 管道状态：同时保留整体与各段结果

Bash 默认以最后一段命令状态作为管道状态。`build | tee log` 中，即使 build 失败，只要 tee 成功，整体也可能是 0。`set -o pipefail` 改成采用最右侧非零状态；仍不能替代对每段失败含义的判断。

```bash
# example: shell-pipeline-status
set -o pipefail
bash -c 'exit 3' | bash -c 'exit 5' | bash -c 'exit 0'
snapshot=("$?" "${PIPESTATUS[@]}")
printf 'overall=%s stages=%s,%s,%s\n' "${snapshot[@]}"
```

预期为 `overall=5 stages=3,5,0`。关键是用**同一条赋值命令**保存 `$?` 与 `PIPESTATUS`。如果先用单独的 `rc=$?`，这条赋值也会成为新命令，从而改变随后看到的 `PIPESTATUS`。

该示例不要预先开启 `set -e`；它故意执行失败管道，再检查结果。在实际脚本中，是否立即退出应由错误契约决定，而不是与示例的检查顺序互相冲突。

`set -e` 有条件判断、逻辑链、函数调用上下文等例外，不能概括成“任何非零就退出”。`set -u` 能发现一部分未设置变量问题，却不证明变量内容正确。把 `set -euo pipefail` 写在第一行之后，仍需设计输入校验、错误分类和清理路径。

### 例题：为什么日志里有 ERROR，脚本仍报告成功？

先检查生产者是否真的返回失败，再检查管道是否隐藏了状态。文本中出现 `ERROR` 不是标准退出码；程序也可能把可恢复告警写到 stderr，最后仍然成功。正确方案应先明确“什么条件代表失败”，然后把状态传递给调用者，不只是搜索一个单词。

## 3.7 文本、文件名与结构化数据

工具应按数据协议选择。`grep` 筛行，`sed` 变换文本流，`awk` 处理记录和字段，`sort` 排序，`uniq` 比较相邻行。它们很适合定义清楚的文本格式，不自动成为 JSON、CSV 或任意二进制解析器。

```bash
# example: shell-counts
printf '%s\n' warn info warn error info info |
  LC_ALL=C sort | uniq -c | sort -nr
```

预期计数为 info 3、warn 2、error 1。`uniq` 只合并相邻的相同行；如果目标是全局计数，需要先让相同值相邻。`LC_ALL=C` 只对它前面直接修饰的命令设置环境；需要固定整个脚本的区域设置时，可以在受控脚本环境里 `export LC_ALL=C`。

通用 CSV 允许引号包围的逗号和换行，因此 `awk -F,` 不等于完整 CSV 解析。JSON 的嵌套与转义同样不能靠一个简单 grep 可靠处理。明确只接受“每行两个无引号字段的简化格式”可以使用简单工具，但应把它称为自己的输入协议，而非通用 CSV。

文件名更不能用空白来随意分割。`for f in $(ls)` 会受到命令替换、分词与路径展开影响，还把面向显示的 ls 输出当作数据协议。GNU 工具可采用 NUL 分隔：

```bash
find . -type f -name '*.log' -print0 |
  xargs -0 -r grep -nH -- 'ERROR'
```

`-print0` 与 `-0` 成对保留文件名边界，GNU `-r` 避免无输入时仍运行命令，`-H` 始终显示文件名。这个例子只检索当前目录，但日志可能包含敏感数据，不应直接上传输出。

NUL 分隔解决的是名字编码问题，不消除从 find 发现名字到 grep 打开文件之间的时间差；在不可信可变目录中还需要更严格的对象访问设计。xargs 也会汇总子命令状态，不能把其返回码当成某一次 grep 的原始返回码。

## 3.8 完整例子：验证并统计课程日志

现在把引用、输入协议与失败状态组合起来。约定标准输入的每行只能是 `info`、`warn` 或 `error`，输出三类计数，顺序固定；空输入合法，得到三个零；任意非法行使程序退出 2，不输出看似完整的统计。输入结尾可以没有换行，文件统一使用 LF，不悄悄剥除 CRLF 中的 CR。输入契约限定为不含 NUL 的文本：Bash 不能可靠保留 NUL，本例不是任意二进制输入的验证器。

```bash
#!/usr/bin/env bash
# example: shell-log-summary
set -u
info=0
warn=0
error=0
line_number=0
line=
while IFS= read -r line || [[ -n "$line" ]]; do
  line_number=$((line_number + 1))
  case "$line" in
    info) info=$((info + 1)) ;;
    warn) warn=$((warn + 1)) ;;
    error) error=$((error + 1)) ;;
    *) printf 'invalid record at line %s\n' "$line_number" >&2; exit 2 ;;
  esac
done
printf 'info=%s\nwarn=%s\nerror=%s\n' "$info" "$warn" "$error"
```

保存为 `log-summary.sh`，用 `bash log-summary.sh` 执行即可，不必先更改执行权限。读取循环中，`IFS=` 避免裁剪记录两端空白，`read -r` 避免把反斜线当转义；`|| [[ -n "$line" ]]` 处理最后一条未以换行结束的记录。

这里没有 `((count++))`，因为算术命令会依据表达式值产生真假状态，而赋值表达式在这一用途下更直观。计数使用 Bash 的固定宽度整数，适合课程规模输入，不是无限精度流分析器；管道传输失败和底层读取错误仍需要调用层的监控与约束，不能只靠这份格式验证器保证完整输入到达。

**验收用例：** 三行 info/warn/info 得到 2、1、0；空输入得到全零；最后一行无换行仍计数；含 `warning`、空白或反斜线的非法行退出 2，且 stdout 为空。最后这个条件可以防止下游误用半份统计。

将该程序的 stdout 接到下一章的不覆盖报告发布器，就得到一个小型两阶段流程：先验证并生成结果，再发布文件。仍要同时处理上游失败，不能让发布器把空输入当作“成功报告”；通常先保存并检查统计阶段结果，再决定是否发布。

## 3.9 常见反模式与替代思路

| 反模式 | 失败原因 | 更合适的方向 |
|---|---|---|
| 拼接字符串后 eval | 数据进入第二次语法解析 | 数组和直接调用 |
| 不加引号传文件名 | 分词或路径展开改变参数 | 引用、数组、必要时使用 -- |
| 输入输出重定向到同一文件 | 输出先截断输入 | 临时输出、校验、发布 |
| 只检查管道最后一段 | 上游失败被掩盖 | pipefail、及时保存 PIPESTATUS、业务判定 |
| 把一切非零视为崩溃 | 工具状态可能包含正常分支 | 按手册分类 |
| 解析 ls 或任意 CSV | 数据协议与工具模型不匹配 | NUL 分隔或结构化解析器 |

改写脚本时，先修复边界和可测试性，再讨论少启动几个进程的性能优化。一个每小时运行一次的维护脚本，通常更需要能解释失败，而不是省下几毫秒。

## 练习与解题提示

**基础层**

1. `show_args ""` 和 `show_args` 分别有几个参数？
2. 为什么 `"$name"` 与 `--` 不能互相替代？
3. `tool 2>error.log | tee output.log` 的 stdout 和 stderr 各去哪里？

**机制层**

4. 管道三段退出 3、5、0，默认状态和 pipefail 状态分别是多少？
5. 为什么先执行 `rc=$?` 再保存 PIPESTATUS 可能失去原管道状态？
6. `producer` 一次写入一条记录，能否保证下游一次 read 恰好读出这一条？

**工程层**

7. 给日志统计脚本设计至少四个反例，并解释哪些应拒绝、哪些应接受。
8. `find -print0 | xargs -0` 是否同时解决文件名特殊字符和攻击者替换文件的竞态？
9. 上游校验失败退出 2，下游把收到的空数据成功写入文件。为何仅检查文件存在仍然不够？

**解题提示与答案**

1. 分别为 1 和 0。2. 引用保护参数边界，`--` 改变选项解释，且不是所有工具都支持。3. stderr 进 error.log，stdout 经 tee 同时到其 stdout 和 output.log。

4. 0 和 5。5. 赋值本身也是新命令，更新了状态；可用一次数组赋值同时保存。6. 不能，管道是字节流，需要自己恢复记录边界。

7. 空输入合法；未换行的合法末行合法；空白行、拼错级别、CRLF 中未约定的 CR、含反斜线记录应拒绝。8. 只解决传递边界，不自动消除名字查找竞态。9. 必须同时验收上游状态、输出语义和发布结果，存在一个空文件不是任务成功证据。

## 小结与参考

Shell 的核心能力是安排执行。可靠脚本保留三类边界：参数边界、流中记录边界、失败语义边界。把输入协议、状态含义和输出条件写清楚，比记忆更多神奇单行命令更有价值。

- GNU Bash Manual：[Shell Expansions](https://www.gnu.org/software/bash/manual/html_node/Shell-Expansions.html)、[Redirections](https://www.gnu.org/software/bash/manual/html_node/Redirections.html)、[Pipelines](https://www.gnu.org/software/bash/manual/html_node/Pipelines.html)。先核对示例涉及的规则，再扩展到不同上下文。
- [pipe(7)](https://man7.org/linux/man-pages/man7/pipe.7.html)：重点读字节流、容量、PIPE_BUF 与 SIGPIPE 的区别，不要把原子写入误解成消息队列。
- GNU Findutils：[Safe File Name Handling](https://www.gnu.org/software/findutils/manual/html_node/find_html/Safe-File-Name-Handling.html)：结合文件名包含空白、换行和短横线的情况阅读。

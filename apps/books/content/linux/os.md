# 操作系统：抽象、保护与资源管理

> 先修：本卷前三章。目标：解释操作系统为什么存在，把进程、地址空间、文件和系统调用放回同一模型，并能区分接口、机制与策略。本章不要求安装内核或修改启动配置。

## 从独占机器到共享机器

假设机器上只有一个程序，它可以直接控制内存和设备。加入第二个程序后，问题不只是“轮流运行”：谁能改谁的内存？设备请求怎样排队？一个程序陷入无限循环怎么办？程序如何在不知道具体磁盘型号的情况下保存数据？

操作系统提供三类能力：用抽象简化设备与资源，靠保护隔离不同执行主体，通过资源管理决定如何共享。进程把一次执行包装为有身份和资源的对象；虚拟地址空间提供受保护的地址视图；文件将持久数据组织为可命名对象。这些抽象不消除物理限制，而是把限制转换为稳定接口和可管理规则。

### 机制与策略应分开

机制回答“如何做到”，策略回答“何时给谁”。定时器中断提供夺回处理器控制权的机制，调度器选择下一任务属于策略；页表支持地址映射，哪些页面回收又属于策略。若把两者混合，常会误以为某一代 Linux 的具体算法就是操作系统必须采取的唯一方案。

## 特权级与受控入口

用户态程序不能任意改变页表根、禁用中断或访问其他主体的受保护内存。处理器的特权机制与内核维护的数据结构共同执行限制。用户态与内核态不是两块互不相关的 CPU，而是同一处理器在不同权限和上下文下执行代码。

### 三种进入内核的原因

- **系统调用**：程序主动请求服务，例如打开文件、建立映射。
- **异常**：当前指令引发同步事件，例如缺页、非法指令、除法错误。
- **中断**：外部设备或定时器等引发事件，与当前指令的业务含义不必相关。

异常不都意味着程序错误。第一次访问合法但尚未建立物理页的地址，可以通过缺页处理正常完成。相反，非法地址也可能触发异常，最终转为进程收到信号；不能把所有 page fault 都当作换盘或崩溃。

系统调用通常在当前任务上下文中进入内核，并不必然切换到另一个任务。因此“发生了模式切换”和“发生了上下文切换”必须分开。后者还涉及保存与恢复调度执行状态，可能改变地址空间和缓存局部性。

## 虚拟化不等于模拟整台计算机

操作系统常被说成“虚拟化 CPU 和内存”：每个程序好像有自己的执行流与地址空间。但这与虚拟机监控器提供整台客体机器的虚拟化不是同一层。

| 技术 | 主要隔离或抽象对象 | 共享边界 |
|---|---|---|
| 普通进程 | 地址空间与执行资源 | 同一内核 |
| 容器相关机制 | 命名视图、资源配额等 | 通常仍共享宿主内核 |
| 虚拟机 | 客体机器接口 | 客体内核之下仍依赖宿主资源 |

Linux namespace 改变一些对象的可见范围，cgroup 管理资源分组与限制。它们不是一对自动等价于完整安全隔离的开关；文件挂载、设备、能力、内核漏洞和管理策略都需要考虑。

### 接口、ABI 与实现

API 描述程序调用接口，ABI 还涉及寄存器、栈、二进制布局和调用约定。一个 C 函数叫 `read`，不表示它必须用同样的机器指令序列进入所有架构的 Linux 内核。POSIX 给出一组可移植接口语义，Linux 是具体系统，发行版又决定工具和软件组合。编译与装载篇会进一步连接这些层。

## 并发产生了新的正确性问题

即使只有一个 CPU，任务交替执行也可能导致竞争。两个任务都执行“读余额—加一—写回”，若中途切换，结果可能丢失一次更新。多核让重叠执行更明显，但竞争不以多核为前提。

操作系统自身也并发：多个 CPU 可同时执行内核路径，设备中断可打断适用上下文。因此内核需要锁、原子操作和对象生命周期规则。内核不是一个每次只替一个程序执行、天然不会竞争的巨型函数。

### 例题：共享状态的所有权

一个日志系统既维护文件描述符，又维护“当前文件已写字节数”。把计数器加锁却允许另一个线程提前关闭并复用描述符，仍可能写错文件。正确性需要同时约束数据状态、资源引用和关闭时机。锁的存在本身不是安全证明，必须先定义不变量，例如“有写者持有引用时，当前文件对象不能被销毁”。

## 性能模型与不可消除的开销

设每个任务执行片段平均有效工作时间为 $q$，模型化的切换开销为 $c$，忽略其他因素时，有效执行比例为：

$$
\eta=\frac{q}{q+c}.
$$

若 $q=4$ 毫秒、$c=0.02$ 毫秒，比例约为 99.50%；若把片段缩短到 0.1 毫秒，则约为 83.33%。更频繁切换可能改善响应，却增加直接开销；真实代价还包括缓存与 TLB 影响，并不是常数。

这个算例不意味着应该无限增大片段。交互任务的等待时间、调度公平性和实时约束都有自己的目标。设计操作系统需要明确优化目标，而不是只最大化单一的利用率。

## 综合推演：一次阻塞读取

沿着“用户程序请求读取，数据暂时不在缓存”的情形，画出以下关系：程序通过接口进入内核；内核检查对象与缓冲区；建立或提交所需 I/O；任务等待；调度器让其他可运行任务执行；完成事件使等待者变为可运行；它之后重新获得 CPU，读取才返回。

不要把“完成事件到达”“任务被唤醒”和“任务马上运行”画成同一个节点。若数据命中缓存，也可能跳过实际设备请求。下一章会沿具体内核执行路径继续拆解。

## 练习与解题提示

1. 为什么系统调用不一定引发任务切换？
2. 定时器中断、调度算法分别更接近机制还是策略？
3. 单核系统上能出现共享计数竞争吗？构造一个交错顺序。
4. 容器内看到的 PID 为 1，能否推出它是宿主机唯一的 init？
5. 将例题中的 $q$ 改为 1 毫秒，$c$ 保持 0.02 毫秒，有效比例是多少？

**答案：** 1. 当前任务可以在内核完成服务后返回，始终没有换成其他任务。2. 前者是提供控制机会的机制，后者是选择规则。3. 能，A 读 0，B 读 0，A 写 1，B 写 1。4. 不能，PID 命名空间提供不同视图。5. $1/1.02\approx98.04\%$；仍只是忽略缓存等影响的模型。

## 小结与参考

操作系统不是命令集合，而是一套抽象、保护和共享资源的执行规则。学习 Linux 内核时，应不断问：这里实现了哪种抽象，维持什么不变量，采用了什么策略？

- [OSTEP](https://pages.cs.wisc.edu/~remzi/OSTEP/)：先读 Introduction、Processes 与 Address Spaces，建立统一抽象。
- [MIT 6.S081](https://pdos.csail.mit.edu/6.S081/2020/)：结合 xv6 观察一个较小内核的保护与系统调用设计；xv6 不是 Linux 的缩小源码副本。
- [南京大学 ICS PA](https://nju-projectn.github.io/ics-pa-gitbook/)：从指令执行、异常与系统接口连接软硬件层。

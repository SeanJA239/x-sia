# 调度、响应时间与资源分配

> 先修：进程状态与线程同步。目标：用一张任务时间表比较周转、等待和响应，理解抢占、公平、优先级及配额的区别。教学算法不等于当前 Linux 调度器的完整实现。

## 调度器优化的不是一个数字

就绪任务可能多于可用 CPU。调度器要选择谁运行、在哪个 CPU 运行、何时重新选择。吞吐、公平、交互响应、能耗和截止期限可能互相冲突。

设任务到达时刻为 $a$，第一次运行时刻为 $s$，完成时刻为 $f$，CPU 服务需求为 $b$。对仅含 CPU 工作、不含 I/O 的教学模型：

$$
T_{\mathrm{turn}}=f-a,\quad T_{\mathrm{response}}=s-a,\quad T_{\mathrm{wait}}=f-a-b.
$$

真实任务若阻塞等待 I/O，不能把整个“非 CPU 时间”都称为等待运行队列。时间定义必须与状态边界一致。

## 手工比较 FCFS 与轮转

三个任务同时在时刻 0 到达，CPU 需求分别为 A=6、B=2、C=1，单位毫秒，忽略切换开销。

### 先来先服务

按 A、B、C 顺序执行，完成时刻为 6、8、9。平均周转为 $(6+8+9)/3=7.667$ 毫秒；首次响应为 0、6、8，平均 4.667 毫秒。长任务挡住短任务，形成 convoy effect 一类现象。

### 时间片为 1 的轮转

执行片段顺序是 A、B、C、A、B、A、A、A、A。C 在 3 完成，B 在 5 完成，A 在 9 完成；平均周转为 $17/3=5.667$ 毫秒，平均首次响应为 $(0+1+2)/3=1$ 毫秒。

![同一组任务在 FCFS 与轮转下具有不同首次响应和完成时刻；轮转能早些服务短任务，但引入更多调度边界。](asset:linux-scheduling)

轮转不是无条件优于 FCFS。加入切换开销、不同到达时间和缓存行为，结果可能变化；时间片太短有额外成本，太长则更像顺序执行。最短作业优先在适用假设下有良好平均等待表现，但需要知道或预测工作量，持续短作业还可能使长任务饥饿。

## 抢占与阻塞是不同事件

阻塞通常是任务自身无法继续，例如等待数据；抢占则是任务还能运行，但调度策略让它暂时让出 CPU。被唤醒任务是否立刻抢占当前任务，取决于调度策略和状态。

主动调用 yield 也不是对其他特定线程的可靠同步方式。若代码正确性依赖“我 yield 一下，对方肯定已经做完”，它仍缺少明确的条件、通知和结果确认协议。

### Linux 的公平调度应怎样理解？

Linux 不同版本的公平类实现持续演进，包括 CFS 历史与 EEVDF 相关演进。可先理解按权重分配服务、跟踪已获服务与目标服务的差异，再阅读目标版本的具体算法。不要把一张历史红黑树示意图当成所有版本不变的执行契约。

nice 影响普通调度下的相对权重，不是“保证拿到几毫秒”，也不把任务自动变成实时任务。机器空闲时，低权重任务仍可能利用空闲 CPU。

### 加权公平的具体推演

在单 CPU、A 与 B 始终可运行的抽象模型中，设权重为 2:1，长期目标服务份额可表示为 2/3 与 1/3。权重不是硬配额：B 阻塞时，不应该让本可运行的 A 只能使用 2/3 CPU 而故意浪费剩余容量。

一种教学虚拟时间模型让任务运行增量 $\Delta t$ 转成 $\Delta v=\Delta t/w$。A 运行 2 单位得到虚拟增量 1，B 运行 1 单位同样得到增量 1，因此可以用相近的虚拟服务进度表达不同权重。实际 Linux 还涉及可运行集合、滞后量、虚拟截止时间等版本相关机制，这个小模型不代替实现。

公平还需要说明范围。如果 A 拆成十个线程，按线程与按用户组公平会得到不同结果。资源分组把管理者想保护的边界加入调度关系，避免“创建更多线程”被误认为自动获得更高应得份额。

## 优先级反转与实时约束

假设高优先级 H 等待低优先级 L 持有的锁，而中优先级 M 不断抢占 L。结果 H 间接被 M 阻挡，这就是优先级反转的典型关系。优先级继承可在适用锁机制中临时提高持锁者的优先级，帮助它释放资源；并不消除临界区本身的执行成本。

实时系统关心满足时间约束，不只是平均速度。最高优先级任务也可能被不可抢占区间、锁、中断或资源竞争影响。实时策略使用不当还能使普通任务饥饿，本章不要求在真实机器上修改实时优先级。

## 多核中的局部性与负载平衡

任务迁移到另一个 CPU 可能改善负载均衡，也可能损失缓存局部性。NUMA 系统中，内存与 CPU 的距离还会影响访问成本；线程在哪运行、数据在哪分配不应完全分开考虑。

CPU affinity 限制可运行的 CPU 集合，配额限制一段周期内可用的总 CPU 时间。允许在 8 个 CPU 上运行且额度为 2 核，并不等于绑定某两个 CPU；任务可能在较短时间内并行消耗额度，然后被节流。

### 配额例题

假设额度为每 100 毫秒最多 200 毫秒 CPU 时间，四个 CPU 上的线程都持续工作。在理想同时运行且没有其他约束的模型下，50 毫秒就能消耗整份额度，之后可能等到补充周期。平均用核仍接近 2，却会出现突发执行与等待交替。延迟敏感任务因此不能只观察平均百分比。

## 可运行的纯模型模拟

这个 Python 模型只有整数列表，不创建线程，不操作真实调度器。

```python
# example: scheduling-round-robin
from collections import deque

remaining = {"A": 6, "B": 2, "C": 1}
queue = deque(remaining)
first, finish = {}, {}
clock = 0
while queue:
    name = queue.popleft()
    first.setdefault(name, clock)
    remaining[name] -= 1
    clock += 1
    if remaining[name]:
        queue.append(name)
    else:
        finish[name] = clock
assert first == {"A": 0, "B": 1, "C": 2}
assert finish == {"C": 3, "B": 5, "A": 9}
print(finish)
```

修改它以加入到达时刻和切换开销时，先写清就绪队列的更新顺序。两个事件发生在同一时刻时，选择哪个先入队会影响结果；模拟器也需要明确契约。

## 练习与解题提示

1. 首次响应很短，是否代表周转时间也很短？
2. 在给定三任务模型中，若按最短作业 C、B、A 执行，完成时刻与平均周转是多少？
3. 为什么更多任务迁移不一定提升吞吐？
4. 优先级继承为什么不能让临界区耗时变为零？
5. CPU 集合为 8 核、平均额度为 2 核，最大瞬时并行度是否必定为 2？

**答案：** 1. 不是，任务可以早获得一次服务却很晚完成。2. 1、3、9，平均 $13/3\approx4.333$ 毫秒。3. 有缓存、迁移和 NUMA 成本。4. 仍要执行持锁者的必要工作，它只调整调度阻挡关系。5. 不是，还需看允许 CPU、线程数与其他约束；平均配额不同于瞬时并行度。

## 小结与参考

调度模型帮助比较目标，而非提供一句适用于所有任务的最佳算法。诊断 Linux 调度，应同时识别状态、调度类别、允许 CPU 与配额边界。

- [OSTEP：CPU Scheduling](https://pages.cs.wisc.edu/~remzi/OSTEP/)：用同一任务集手算 FCFS、SJF、轮转和反馈队列。
- [Linux scheduler documentation](https://docs.kernel.org/scheduler/index.html)：按目标内核版本理解公平与实时调度机制。
- [sched(7)](https://man7.org/linux/man-pages/man7/sched.7.html)：核对用户可见策略、优先级与权限要求。

# 系统观察与可靠自动化

> 先修：Linux 前三章，能够区分进程状态、文件引用和管道退出码。环境：Linux；部分观察命令来自 procps、util-linux、sysstat，未安装时先查已有工具，不要求 sudo 或安装软件。目标：用有定义、有时间窗口的证据区分瓶颈，并把观察结果交给一个有失败契约的发布脚本。

## 14.1 先定义症状，再选择工具

“系统很慢”至少可能表示五件不同的事：一次请求响应慢，一批任务完成慢，单位时间产出少，启动等待长，或者交互时偶尔卡顿。不同症状需要不同指标。把它们都替换成 CPU 百分比，会从第一步就失去诊断方向。

一份最小问题记录应包含：观察对象、开始与结束时间、预期行为、实际行为、输入规模、允许使用的资源、最近发生的相关变更。时间窗口尤其重要：早上出现的故障，不能仅靠下午的一张正常截图解释。

![图 14-1：单条执行路径的墙钟时间包括排队、执行与等待。图中宽度是示意，不是本机测量；多个线程的 CPU 时间可重叠。](asset:linux-observe)

采用“假设—可区分的证据—后续动作”的顺序。例如假设 CPU 不够，就寻找运行队列、应用允许用核数与累计 CPU 时间；假设等待存储，就寻找等待时间、I/O 延迟和请求路径。某个指标变化若无法区分两个假设，继续盯着它并不会增加多少信息。

不要一开始同时加线程、清缓存、重启服务并更换配置。即使问题暂时消失，也无法知道哪项动作有效。先记录，再做范围明确的单项调整；共享或生产环境的变更还需要对应授权，本章不要求执行这些变更。

## 14.2 指标有四种常见形态

| 形态 | 示例 | 应怎样读取 |
|---|---|---|
| 瞬时量 | 当前队列长度、当前 RSS | 连续采样看趋势，单点容易错过峰值 |
| 累计计数器 | 累计 CPU 微秒数、累计读字节数 | 对同一对象取差并除以时间窗口 |
| 比率或利用率 | 某区间平均用核数 | 必须说明分子、分母与统计范围 |
| 分布 | 请求延迟的 p50、p95、p99 | 保留样本数、窗口和分位数定义 |

对于没有重置或溢出的累计计数器 $C(t)$，在同一身份对象上测得：

$$
r=\frac{C(t_1)-C(t_0)}{t_1-t_0}.
$$

如果进程在两次采样之间重启，PID 被复用，或计数器发生重置，直接相减就失去原义。监控系统需要把对象身份和计数器生命周期一起处理，而不是遇到负差值就随意改成零。

### 例题：从累计 CPU 时间算用核数

下面所有数字都是教学数据，不是实际机器结果。一个 cgroup 的累计 CPU 使用从 12,000,000 微秒增长到 18,000,000 微秒，两次采样相隔 4 秒。CPU 时间增量是 6 秒，所以平均用核数是 $6/4=1.5$。若边界最多允许 2 核，可说相对这个上限平均使用约 75%；若拿宿主机 32 核作分母，就会隐藏应用自己的容量约束。

平均值也会掩盖突发。前两秒用满两核、后两秒用一核，与整个四秒平稳用 1.5 核具有相同平均值，但排队和响应时间可能不同。

## 14.3 CPU 利用率、负载与配额

Linux load average 反映可运行任务和不可中断等待任务数量的平滑统计，通常显示 1、5、15 分钟尺度的值。它不是百分比，也不是严格的“最近一分钟任务数算术平均”。磁盘等待相关的 D 状态任务可以使负载升高，即便 CPU 仍有空闲。

```bash
uptime
ps -eo pid,ppid,stat,pcpu,pmem,comm --sort=-pcpu
vmstat 1 5
```

这些都是观察命令，但输出仍可能包含不适合公开的进程名称或系统信息。只保存诊断所需字段，不把完整机器快照自动同步到外部平台。

`ps` 的 `%CPU` 通常基于进程寿命内的累计平均，与 top 某刷新区间的数值不可直接等同。`vmstat` 第一行的许多统计项反映自启动以来的平均，后续行才对应指定间隔；某些字段仍是即时量，要按工具手册解释。

虚拟机还可能存在 steal 时间：虚拟 CPU 想运行，但宿主调度没有给它执行机会。容器可能受到 cgroup CPU 配额约束；cpuset 则限制能在哪些 CPU 上运行，两者不等价。

在 cgroup v2 中，`cpu.max` 常以“额度、周期”给出限制。例如 `200000 100000` 对应平均额度约为：

$$
c_{\mathrm{quota}}=\frac{200000\,\mu\mathrm{s}}{100000\,\mu\mathrm{s}}=2.
$$

这不是固定绑到某两颗 CPU。额度可能在周期内提前用完，引发节流；父层 cgroup、cpuset 和其他调度约束还可能进一步限制实际可用资源。查看哪个 cgroup 应根据当前进程所在层级确定，不要照抄网上另一个容器的路径。

### 反例：8 核机器 load 为 8，是否恰好健康满载？

不能这样判断。八个任务可能在等 I/O；应用可能只获两核配额；某个串行线程还可能占满一个核，而其余核空闲。至少要结合状态、运行队列、CPU 使用和资源边界，才能决定瓶颈属于计算、调度还是等待。

## 14.4 内存：地址、驻留、缓存与压力

进程虚拟地址空间表示它建立的地址映射范围，不等于立即占用的物理内存。一个很大的保留映射可能只有少量页面真正驻留；相反，小块对象频繁分配、复制或共享，也会带来复杂的实际成本。

RSS 统计驻留页面，共享页可能在多个进程里重复计入。PSS 按共享者比例分摊，更适合讨论一组相关进程的占用贡献；读取 PSS 也有成本和权限要求，不必为了每秒刷新一个漂亮数字而无节制扫描所有进程。

### 例题：为什么两个进程的 RSS 不能直接相加？

假设两个进程各有 100 MiB 私有驻留页，共享 60 MiB，并且这些共享页只由这两个进程映射。每个 RSS 是 160 MiB，相加得到 320 MiB；按此简化模型，唯一物理页总量却是 $100+100+60=260$ MiB。每个 PSS 为 $100+60/2=130$ MiB，相加才与这部分物理页量一致。真实系统还包含内核开销、其他共享者及不断变化的映射。

Linux 会利用空闲内存作为页缓存。`free` 中的 free 很小而 available 较大，可能只是缓存利用充分。available 是估计值，不是保证新分配必定成功的承诺；回收脏页需要写回，锁页和内核条件也会限制回收。

更有解释力的组合是：同一负载下进程占用是否持续增长，available 是否下降，是否发生回收或交换活动，应用延迟是否同时恶化。已经存在少量 swap 数据，不代表此刻正在发生频繁换入换出；应看活动速率而不是只看库存。

发生 OOM 时还要区分宿主机压力与 cgroup 边界。容器触及自己的 `memory.max` 时，宿主机仍可能有空闲内存；看到进程消失也不能直接判定 OOM，要结合对应事件记录与退出原因。不要通过关闭所有内存限制来“证明”程序没有问题。

## 14.5 存储：容量、速率、延迟与并发

`df -h` 看文件系统空间，`df -i` 看 inode 使用，`du` 遍历名字统计对象占用，它们回答不同问题。若剩余字节很多却不能新建文件，要检查 inode、配额、只读状态以及权限，而不是只重新运行一次 df。

性能方面，顺序大块传输适合用字节每秒描述，小块操作还受 IOPS 与延迟约束。在串行发起、下一次操作必须等前一次完成的模型下，单次平均延迟为 $L$ 秒，则：

$$
\mathrm{IOPS}\leq\frac{1}{L}.
$$

例如 2 毫秒对应约 500 IOPS。若每次读取 4 KiB，则数据率约为 $500\times4096=2{,}048{,}000$ 字节每秒，约 1.95 MiB/s；它和设备宣传的顺序 GB/s 不是同一工作负载。

若长期平均有 $Q$ 个操作在途，稳定且统计范围一致时可用 $Q\approx\lambda L$ 联系并发数、完成速率和平均延迟。代入 $Q=8$、$L=2$ 毫秒，得到候选速率 4000 IOPS，但这**不是设备保证**：增加并发通常会改变延迟，设备还可能有吞吐上限。公式是检查量纲与关系的工具，不能把旧延迟当成任意加并发时都不变。

已安装 sysstat 时，可用 `iostat -xz 1 3` 观察设备统计，但默认首份报告常覆盖较长历史。`await` 包含排队和服务等影响，`%util` 在多队列设备上也不能简单解释为“距峰值吞吐还差多少”。没有对应硬件和工作负载，就不要根据一个阈值宣布磁盘损坏。

## 14.6 网络与应用：连通不等于正确

把网络问题拆成名字解析、路由、连接、身份校验、应用协议与业务语义。DNS 能解析不代表端口可达；TCP 建立不代表证书或 SSH 主机身份可信；HTTP 返回 200 也不一定表示正文满足业务需求。

观察延迟时，平均值可能隐藏尾部。下面给出一组明确排序的教学样本，单位毫秒：10、10、10、10、10、10、10、10、10、1000。平均值是 109，中位数是 10。采用 nearest-rank 定义时，p95 取第 $\lceil0.95\times10\rceil=10$ 个样本，为 1000。不同分位数插值定义可能产生不同值，因此需要写清方法；仅十个样本也不足以稳定刻画稀有尾部事件。

请求重试会改变看到的吞吐和延迟。一项业务操作可能产生多次网络请求，统计“请求成功率”与统计“用户操作成功率”不是同一分母。排查前应把请求 ID、重试次数与最终结果关联起来，但不得把认证头、访问令牌或私人正文混进公开日志。

网络工具的使用边界同样重要。本章不扫描远程网段或陌生端口；需要复现时使用自己管理的本地服务，后续机制见[网络路径与 SSH 信任](book:servers/network)。

## 14.7 压力指标与证据矩阵

PSI 表示任务因 CPU、内存或 I/O 资源不足而停顿的时间信息，而非直接报告资源利用率。`some` 关注至少有任务受影响的情况，`full` 在适用资源和统计范围下关注所有非空闲任务同时受阻的情况；CPU 的 full 含义、是否有值等与内核版本和系统级/cgroup 级范围有关，应查对应文档。

可以在系统提供且权限允许时查看 `/proc/pressure/` 中的相关文件。指标提供新的证据维度，但不能单凭 PSI 大于零就要求扩容；短暂资源竞争在正常系统中也可能发生。

![图 14-2：先定义症状，再对齐时间窗口与资源范围，收集区分假设的证据，最后做单项有边界的验证。CPU、内存、I/O 等候选并非互斥。](asset:linux-diagnosis)

| 现象 | 候选假设 | 能增加区分力的证据 | 不宜直接采取的动作 |
|---|---|---|---|
| CPU 低、延迟高 | I/O、锁、外部服务、节流 | 请求耗时分解、线程等待、配额事件 | 直接更换 CPU |
| free 低、available 高 | 正常缓存利用 | 应用占用趋势、压力与回收活动 | 清缓存后宣称泄漏解决 |
| load 高、CPU 有空闲 | D 状态等待或资源边界 | 状态分布、设备延迟、允许用核数 | 不看对象就杀任务 |
| 磁盘剩余字节足够但创建失败 | inode、配额、权限、只读挂载 | 错误信息、df -i、对象权限 | 对整棵树 chmod 777 |
| 进程退出却无合格结果 | 输入、程序契约或输出路径错误 | 退出码、校验日志、产物检查 | 仅凭进程消失判定完成 |

观察也有成本。频繁抓取堆栈、扫描目录或读取大量进程细节会扰动系统。采用能回答问题的最小采样频率与最少字段，故障解除后停止临时采集；不要让排查工具成为新的负载来源。

## 14.8 脚本契约：输入、输出、副作用和失败后状态

将观察结果保存为报告时，先决定这些规则：目标路径由谁提供，是否允许覆盖，空输入是否合法，谁可以访问父目录，失败后是否会留下完整或部分对象。没有这些前提，“可靠保存文件”不是一个明确需求。

下面的发布器接受一个目标路径，从 stdin 复制字节。目标必须不存在，父目录必须已存在且由调用者信任；要求 GNU 工具与支持同目录硬链接的文件系统。空输入合法，临时文件继承 mktemp 的限制模式。它不负责解释报告内容，内容校验应在调用前完成。

```bash
#!/usr/bin/env bash
# example: observe-publish
set -u
if [[ $# -ne 1 || -z "$1" || "$1" == */ ]]; then
  printf 'usage: bash publish-report.sh TARGET\n' >&2
  exit 2
fi
out=$1
if [[ -e "$out" || -L "$out" ]]; then
  printf 'refusing existing target\n' >&2
  exit 2
fi
tmp=$(mktemp -- "${out}.tmp.XXXXXX") || exit 3
trap 'rm -f -- "$tmp"' EXIT
trap 'exit 129' HUP
trap 'exit 130' INT
trap 'exit 143' TERM
if ! cat > "$tmp"; then
  printf 'input copy failed\n' >&2
  exit 4
fi
# 最终创建操作本身拒绝覆盖；不能只依赖前面的检查。
if ! ln -T -- "$tmp" "$out"; then
  printf 'publish refused\n' >&2
  exit 5
fi
printf 'created: %s\n' "$out"
```

保存为 `publish-report.sh`，在自己新建的临时目录内测试：

```bash
lab=$(mktemp -d) || exit 1
printf 'scope=teaching\nstatus=checked\n' |
  bash publish-report.sh "$lab/report.txt"
cat -- "$lab/report.txt"
# 再次向同一目标发布应失败，原内容必须保持不变。
printf 'replacement\n' | bash publish-report.sh "$lab/report.txt"
```

最后一条命令故意失败。实际流水线还应按上一章的方法检查生产者状态，避免生产者失败却把空报告成功发布。本例的输入由 printf 产生，验证的是发布行为，不是完整监控系统。

### 为什么要临时文件加硬链接？

直接向目标 `>` 写入，读者可能看到半份数据。先写临时文件，使未完成内容保持在临时名字下；写完后用不覆盖的硬链接创建目标，让目标一旦出现就引用已经写完的对象。`ln -T` 防止目标被解释成“把临时文件放进这个目录”。

最初的存在检查用于给出清楚错误，但检查之后可能有另一个执行者抢先创建目标。最终 ln 会拒绝已存在的目标，因此并发发布者中至多一个能成功创建同一名字；先检查再直接覆盖则没有这种保证。

这只讨论信任父目录、同一文件系统和没有后续修改的模型。不适用于攻击者能替换路径组件的目录，也不自动保留旧文件权限、提供版本替换或同步落盘。更多持久化保证需要上一章讨论的文件及目录同步协议。

## 14.9 失败矩阵、重试与完成判据

| 失败时刻 | 可能保留的状态 | 调用者应该怎么做 |
|---|---|---|
| 参数或已有目标被拒绝 | 未创建新的目标 | 核对参数，不覆盖原文件 |
| 临时文件创建失败 | 目标尚未发布 | 查看父目录、权限、空间等错误 |
| 输入复制失败 | 临时内容不完整，正常退出清理 | 不把临时内容作为合格结果 |
| 并发者先发布 | 已有另一份目标，自己的临时文件清理 | 比较身份或按业务策略处理冲突 |
| 发布成功、清理前被强制终止 | 可能同时存在完整目标与临时名字 | 按自己的临时文件归属清理，不能乱删 |
| 断电或机器崩溃 | 本脚本不提供持久性承诺 | 按恢复协议校验，不仅看文件是否存在 |

trap 不能处理 SIGKILL 或断电。Bash 等待前台命令时对信号陷阱的执行也可能延后，不应声称“收到信号瞬间一定清理完成”。重试同一目标会被拒绝，这是避免覆盖的契约，不是完全自动的幂等业务接口。

可靠重试需要进一步知道“已有目标是不是这次请求的正确结果”。可以设计请求身份、内容摘要和版本策略，但不要把每次重试都生成一个新随机名字就称为解决了重复执行；那只会让重复结果更难看见。

任务完成至少应包含三层证据：执行已结束且状态被收集，输出满足格式与内容约定，发布或持久化满足所要求的级别。进程退出、端口监听、CPU 降到零、目录中出现一个文件，分别只是局部证据。

## 14.10 综合任务：从日志到不可覆盖的报告

将上一章日志统计器与本章发布器组合，但不要直接无条件管接管。先在自己的临时工作区运行统计器，明确检查它返回 0 且结果包含三项预期计数，再调用发布器。完成后比较发布文件与已验证内容，收集两阶段退出状态。

设计四种输入：正常日志、空日志、含非法记录、目标已经存在。前三种的内容语义由统计器判定，最后一种由发布器拒绝。再让两个发布进程竞争同一个新名字，检查最多一个成功、目标内容来自一个完整候选，而不是两份数据混合。

这里的目标是证明一组受限软件行为，不是测量机器性能。不要为了演示内存压力而分配到 OOM，不要为了演示磁盘满而填满共享盘，也不要向不属于自己的进程发送信号。

## 练习与解题提示

**基础层**

1. free 很少、available 很多，能否直接判定内存泄漏？
2. 为什么不能不看定义就把 ps 的 CPU 数字与 top 的一帧作比较？
3. 串行 I/O 从 4 毫秒降到 1 毫秒，理想 IOPS 上限如何变化？

**机制层**

4. 两个进程各有 80 MiB 私有页，共享 40 MiB 且没有其他共享者，RSS 合计与这一模型的唯一页量分别是多少？
5. 一个累计 CPU 计数器在 5 秒内增加 10 秒 CPU 时间，平均用核是多少？为什么不是“不可能”？
6. `cpu.max` 额度除以周期为 2，是否意味着程序固定在编号 0 和 1 的 CPU 上运行？

**工程层**

7. 发布前检查目标不存在，为什么仍要最终 ln 拒绝覆盖？

## 小结与参考

可靠观察要说明对象、时间窗口、资源边界和统计定义；可靠自动化要说明输入协议、输出承诺和失败后状态。工具可以提供证据，但不会替代这些判断。先把一个有边界的小流程做对，再扩展监控、并发和恢复能力。

- Linux man-pages：[proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html)、[proc_loadavg(5)](https://man7.org/linux/man-pages/man5/proc_loadavg.5.html)：核对 proc 的字段来源与 load 的统计对象。
- Linux Kernel Documentation：[PSI](https://docs.kernel.org/accounting/psi.html)、[Control Group v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)：重点读 scope、cpu.max、cpu.stat、memory.current 与限制事件，不复制别人的路径。
- [GNU Coreutils Manual](https://www.gnu.org/software/coreutils/manual/coreutils.html)：核对 mktemp、ln、df、du 的行为和失败条件。
- [Google SRE Book：Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)：学习从用户症状组织监控，不把主机利用率当作全部服务质量。
- [鸟哥的 Linux 私房菜](https://linux.vbird.org/)：配合进程与资源观察命令练习。本文数值均为明示的教学算例，未引用私人机器的测量数据。

**操作验证边界：** 本章发布器可在支持 GNU 硬链接语义的本地临时目录做软件回归；Linux 资源统计、cgroup、PSI 与真实存储行为需另在相应环境检查。截图或页面构建成功不等于技术、硬件或生产恢复验证完成。

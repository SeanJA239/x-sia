# 文件、目录与权限模型

> 先修：[系统、进程与执行边界](book:linux/process)。环境：Linux、GNU coreutils；一个可选程序使用 Python 3 标准库。目标：沿路径解释查找与权限检查，用实际对象关系预测链接、删除和文件偏移，并区分可见性与持久性。操作只在自己新建的临时目录进行，不修改系统权限。

## 2.1 路径不是磁盘地址，而是一系列查找

`/home/student/report.txt` 可以分成起点 `/` 与三个名字。内核逐级在目录中查找下一部分，最后取得目标对象。相对路径从进程当前工作目录开始；`openat()` 等接口还能相对于指定的目录描述符查找，这使程序不必把全部逻辑依赖于一个可变的工作目录。

一个名字查找失败，不一定表示末尾文件不存在：中间目录可能不存在，某级目录缺少搜索权限，符号链接可能指向失效路径，也可能出现符号链接循环。遇到错误，先区分“不能经过这条路”和“路的末端没有对象”。

挂载点把另一个文件系统接入同一棵目录树。因此 `/home` 与 `/tmp` 可以来自不同设备，也可以来自同一文件系统；路径长短与磁盘物理位置无直接关系。容器还可能有自己的挂载命名空间：两个进程使用同一个路径字符串，看到的对象未必相同。

路径字符串也有语法边界。Linux 文件名不能包含 NUL 字节和作为路径分隔符的 `/`，但可以包含空格、换行、通配符字符和前导短横线。名字能被文件系统保存，不代表它适合直接进入 Shell 命令字符串。传递名字时必须保留参数边界，下一章会专门处理。

## 2.2 四层对象：目录项、inode、打开文件描述、描述符

先用四个问题区分容易混淆的术语。

| 层次 | 回答的问题 | 保存的典型内容 |
|---|---|---|
| 目录项 | 这个名字对应谁？ | 名字到文件对象的关联 |
| inode | 这是哪种对象、谁能访问？ | 类型、所有者、模式、大小、时间、数据定位 |
| 打开文件描述 | 这一次打开读到哪里了？ | 文件偏移、打开状态标志、对象引用 |
| 进程文件描述符 | 本进程用哪个编号引用它？ | 描述符表中的小整数及每描述符标志 |

普通文件的名字不存储在其 inode 里。两个名字可以指向同一 inode，inode 也不保证永远不变或永不复用。跨文件系统区分对象，通常至少看设备身份与 inode 号这一对；它不是永久的业务主键。

![图 2-1：目录项通过 inode 指向文件对象；进程的描述符经打开文件描述保持访问状态。硬链接共享对象，符号链接保存另一条路径。](asset:linux-files)

独立调用两次 `open()`，通常得到两个不同的打开文件描述，即使它们最终访问同一 inode，也有各自的偏移。`dup()` 复制描述符，则让两个编号引用同一个打开文件描述；它们因此共享偏移。fork 后父子对应的描述符也可以引用相同的打开文件描述。

### 动手：同一文件，为什么有两种偏移关系？

以下 Python 程序使用内存之外的临时文件，但不依赖私人文件或第三方包。

```python
# example: files-offset
import os
import tempfile

with tempfile.TemporaryDirectory(prefix="wiki-offset-") as directory:
    path = os.path.join(directory, "sample.bin")
    with open(path, "wb") as output:
        output.write(b"abcdef")
    with open(path, "rb", buffering=0) as first, open(path, "rb", buffering=0) as second:
        duplicate = os.dup(first.fileno())
        try:
            print(os.read(first.fileno(), 2).decode("ascii"))
            print(os.read(duplicate, 2).decode("ascii"))
            print(os.read(second.fileno(), 2).decode("ascii"))
        finally:
            os.close(duplicate)
```

预期输出依次为 `ab`、`cd`、`ab`。第一次读把共享偏移推进到 2，所以从 duplicate 再读得到 `cd`；独立打开的 second 仍从 0 开始。这里故意使用无缓冲的二进制文件对象与 `os.read()`，避免用户态预读缓冲掩盖内核偏移。

由此可推导：同一 inode 不等于同一读取位置；不同描述符编号也不等于彼此独立。要解释并发读取，必须把这两种“相同”分开。

## 2.3 硬链接、符号链接与重命名

**硬链接**增加同一 inode 的另一个目录项，不复制一份独立文件内容。它通常不能跨文件系统，普通用户也通常不能给目录创建硬链接。修改某个硬链接对应的内容，会从另一个名字看到变化，因为它们引用同一对象。

**符号链接**是另一种文件对象，内容是目标路径。它可以跨文件系统，也可以指向暂时不存在的目标。相对目标以符号链接所在目录为基准解析，不是以调用程序当前目录为基准。

```bash
# Linux 动手练习：保留目录供检查，不自动删除。
lab=$(mktemp -d) || exit 1
printf 'lab=%s\n' "$lab"
printf 'alpha\n' > "$lab/original.txt"
ln -- "$lab/original.txt" "$lab/hard.txt"
ln -s -- original.txt "$lab/soft.txt"
ls -li -- "$lab"
stat -- "$lab/original.txt" "$lab/hard.txt" "$lab/soft.txt"
mv -- "$lab/original.txt" "$lab/renamed.txt"
cat -- "$lab/hard.txt"
```

最初 original 与 hard 的 inode 应相同，链接计数为 2；soft 是独立的符号链接。重命名后 hard 仍能读到 `alpha`，soft 则因为目标名字消失而悬空。可以用 `readlink -- "$lab/soft.txt"` 查看它保存的字符串，得到的仍是 `original.txt`。

`stat` 默认观察符号链接本身，GNU `stat -L` 则跟随链接观察目标。做题时先说明是否跟随链接，否则两份看似冲突的 inode 记录可能都正确。

同一文件系统中的 rename 通常可以原子地改变名字关联；跨文件系统的 `mv` 可能转为复制再删除。不要根据同一个命令名字，假设底层永远只有同一种原子操作。

## 2.4 删除名字，不等于立即释放或安全擦除

删除普通文件名通常执行 unlink，减少目录中的名字引用。当链接计数变成 0，但某个进程仍保持打开引用时，数据仍可被该进程使用。等最后相关引用关闭后，文件系统才有条件回收空间；快照、特殊文件系统策略等还可能影响实际回收。

![图 2-2：unlink 删除最后一个名字后，目录遍历已看不到文件，但仍打开的描述符继续引用对象；关闭最后引用后才可能回收存储。](asset:linux-unlink)

这解释了一个常见现象：`du` 沿名字遍历目录已经找不到旧日志，而 `df` 仍显示空间被占用。另一个原因可能是快照、保留块、挂载覆盖或统计口径差异；不能只凭两者不相等就下结论。

在 Linux 上，排查打开但已删除的文件可以查看自己进程的 `/proc/PID/fd`，或在工具已安装且权限允许时使用 lsof。输出可能包含私人路径，不应原样公开。知道占用者后，应通过其正常关闭或重新打开日志的接口处理，不应把“清理空间”直接等同于强杀进程。

删除也不是安全擦除。SSD 的磨损均衡、快照、远端副本和备份可能保留内容。敏感数据应在收集前设计加密、密钥和保留策略，而不是事后依赖一次 `rm` 或一次覆写。

## 2.5 权限检查必须结合对象类型

传统模式位按所有者、所属组、其他用户分三类，每类包含读、写、执行。用二进制权重表达：

$$
p=4r+2w+x,\qquad r,w,x\in\{0,1\}.
$$

`640` 因而表示所有者读写、组只读、其他无权限。普通模式位检查不是把三类权限加起来：如果身份符合所有者类别，就按相应规则处理，不能因为所有者位不允许而自动改用更宽松的 other 位。ACL、能力、强制访问控制和挂载属性等还可能改变最终结果。

| 权限 | 普通文件 | 目录 |
|---|---|---|
| r | 读取内容 | 枚举目录项名字 |
| w | 修改内容 | 在满足其他条件时增删或重命名目录项 |
| x | 执行许可的一部分 | 搜索目录，按已知名字查找下一层 |

目录 r 和 x 的区别尤其重要：只有 r 时可能列出名字，却无法取得每个子对象的属性；只有 x 而没有 r 时，可能无法列目录，但若已知一个名字，仍可搜索到它。是否能读取末尾文件，还要看文件本身权限。

### 例题：文件可读，路径为什么仍然报错？

假定某普通组成员需要读取 `/srv/course/result.txt`。文件是 `0640` 且组身份匹配，但 `/srv/course` 是 `0700`，目录所有者是另一个用户。即使文件的组读位允许，读者也不能搜索经过该目录，因此访问失败。修复应定位缺少的搜索权限并按共享需求最小化调整，不是对整棵树执行 `chmod -R 777`。

### 例题：只读文件为什么还能被删除？

文件 `note.txt` 为 `0444`，而你对父目录有写和搜索权限；在没有粘滞位、ACL、只读挂载等额外阻碍时，你可能删除它的名字，因为改变的是父目录中的关联，不是写入文件内容。某些命令会额外询问确认，那是工具的交互保护，不等于内核把文件读位重新解释成防删除位。

执行位也不等于“任何程序都能执行成功”：解释器或动态加载器可能不存在，格式可能错误，挂载点可能设置 noexec。反过来，把可读文本交给 `bash script.sh` 时，是 Bash 在读取文本，不等同于直接执行这个文件。

## 2.6 umask、特殊位与共享目录

在没有默认 ACL 等额外规则时，创建模式来自请求位与掩码的按位运算：

$$
M_{\mathrm{actual}}=M_{\mathrm{requested}}\mathbin{\&}\neg U.
$$

普通文件常请求 `0666`，目录常请求 `0777`；umask 为 `0027` 时分别得到 `0640` 和 `0750`。umask 只清除请求中的位，不会给普通文件凭空加执行位。

| 请求模式 | umask | 结果 | 逐位解释 |
|---|---|---|---|
| 0666 | 0027 | 0640 | 清掉组写和其他全部权限 |
| 0777 | 0027 | 0750 | 目录的组执行位保留 |
| 0600 | 0022 | 0600 | 没请求组和其他读位，不会自动得到 |
| 0666 | 0333 | 0444 | 重叠的写位清除，不能用普通减法替代 |

最后一行是反例：`0666 - 0333` 得到的数不是正确的权限结果。把八进制数逐位展开为 r/w/x，再清除屏蔽位，才是通用方法。

需要临时修改 umask 做练习时，可以在圆括号子 Shell 中操作，避免意外改变后续交互会话的创建策略。程序也可能请求更严格的模式，例如 `mktemp` 创建的文件通常不会简单套用“普通文件最终应为 0644”的记忆规则。

目录的 **setgid 位**常用于让新对象继承目录组，但它不自动赋予所有成员写权限；还要考虑请求模式、umask 和默认 ACL。目录的 **sticky 位**常见于共享临时目录，限制谁能删除或重命名其中的条目，通常涉及文件所有者、目录所有者及特权身份。它不阻止具有写权限的用户修改文件内容。

setuid/setgid 可执行文件有更复杂的身份语义，不应通过给自己的脚本随意加特殊位来“解决权限问题”。先学习最小权限、受控管理接口与对应系统的安全机制。

## 2.7 文件大小、实际分配与时间戳

`stat` 的逻辑大小描述文件可寻址的数据范围；实际分配块数描述存储分配。稀疏文件可以在很大的逻辑范围内保留洞，读取洞通常得到零，却不为每个零分配数据块。因此 `ls -l` 显示很大，不一定表示磁盘已经消耗同样多空间。

GNU `du` 默认偏向统计分配占用，`du --apparent-size` 更接近表观大小。压缩、写时复制、共享 extent 和文件系统元数据又会让“文件占几字节”具有多个合理答案。比较时要先统一定义。

时间戳也需要区分：mtime 关联内容修改，ctime 关联 inode 状态变化，atime 关联访问，但可能受 relatime、noatime 等策略影响。ctime 不是通用的“创建时间”；一些文件系统支持 birth time，也不能假定任何工具和文件系统都提供它。

文件修改时刻相同不保证内容相同，大小相同也不保证内容相同。内容哈希可以帮助比较字节身份，但校验值应来自可信渠道；攻击者如果同时替换文件与旁边的哈希文件，单独重新计算不能证明来源可信。

## 2.8 写入、原子替换与断电持久性

把文件更新分成三个层次，就不会把 flush、rename 和 fsync 混为一谈。

1. **程序缓冲层。** 语言运行库可能先保留数据；flush 使该层已缓存数据交给下一层。
2. **内核与文件系统层。** `write()` 成功可能只是数据进入页缓存；`fsync()` 请求把相应状态同步到存储，需要检查错误。
3. **名字与恢复层。** 改变目录项关系，与同步文件内容是不同问题；掉电后名字能否按预期恢复，还涉及目录同步与文件系统语义。

一种常见的同目录更新协议是：创建唯一临时文件 → 完整写入 → 校验 → flush 并同步文件 → rename 到目标 → 同步父目录。它体现的是设计思路，具体实现必须检查每步返回值，并考虑权限保留、符号链接、并发更新和文件系统支持。不要用一行 `mv` 就宣称具备全场景事务和断电保证。

原子替换保护的是名字切换的可见性：新打开的读者看到旧对象或新对象，而不是“半个目录项”。已打开旧对象的读者可以继续读旧内容，不会因为名字指向新 inode 就自动切换。内容的其他并发写入也不会因为 rename 自动消失。

“先检查不存在，再写入”存在检查与使用之间的竞态。需要不覆盖语义时，应让最终创建操作本身拒绝已存在对象，例如适当的排他创建或硬链接发布，而不是只依赖此前的 `test -e`。下一章后的[可靠自动化](book:linux/observe)给出完整的限定环境脚本。

## 2.9 综合任务：给一个共享结果目录设计规则

设两个普通用户属于课程组，需要读取同一份结果；只有负责生成结果的账号可以发布新版本。先写出操作矩阵：谁能搜索目录、谁能枚举名字、谁能读内容、谁能写目录项，而不是先选一个顺眼的三位数字。

然后检查三条访问路径：生成者创建临时文件并发布，读者打开当前结果，旧读者继续持有旧描述符。对每条路径标明权限检查发生在哪里。不要在共享系统上直接实施这份练习；先用纸面推演或自己管理的独立测试环境验证。

最后提出恢复问题：生成过程中退出会留下什么？结果名字切换后是否还需要同步目录？两名生成者同时运行时，是拒绝第二次发布，还是允许明确的版本替换？这些选择应成为数据管理契约，而不是由最后一条命令碰巧决定。

## 练习与解题提示

**基础层**

1. 两个文件的 inode 号相同，是否一定是同一对象？还要看什么？
2. 符号链接保存 `../data/a.txt`，移动链接后为什么可能失效？
3. 请求模式 `0666`、umask `0077` 的结果是什么？请求 `0600`、umask `0022` 呢？

**机制层**

4. 两次独立 open 与一次 open 后 dup，读取偏移的关系有何不同？
5. 普通文件模式 `0444`，能否据此保证别人无法删除它？
6. 删除所有硬链接后，仍打开的读者为何能继续读取？

**工程层**

7. `df` 与 `du` 差很多，写出至少三个候选原因，不要直接断言文件系统损坏。
8. rename 成功后马上断电，能否只凭成功返回就保证新版本一定恢复？
9. 一个哈希文件和数据文件都从未知来源下载，哈希一致能证明作者身份吗？

**解题提示与答案**

1. 还要看设备或文件系统身份，且 inode 可能复用。2. 相对目标的解析基准是链接所在目录。3. 分别为 `0600` 与 `0600`，掩码不能增加未请求的位。

4. 独立 open 通常独立偏移，dup 共享打开文件描述及偏移。5. 不能，删除主要检查父目录，还受 sticky 等规则约束。6. 打开引用继续保持对象存活，名字引用与打开引用不同。

7. 打开但已删除文件、快照或共享块、保留空间、被挂载覆盖的内容，以及遍历权限与统计口径都需排查。8. 不能；文件和目录持久化、设备与文件系统语义仍需考虑。9. 不能，只能说明这两个不可信输入彼此相符，需要可信的发布渠道或签名体系。

## 小结与参考

路径提供查找过程，inode 描述对象，打开文件描述保存访问状态，文件描述符是进程内引用。权限解释依赖对象类型，更新保证依赖文件系统与应用协议。理解这些机制，才能正确处理读写、共享、删除和恢复，而不是靠批量放宽权限掩盖问题。

- [inode(7)](https://man7.org/linux/man-pages/man7/inode.7.html)、[umask(2)](https://man7.org/linux/man-pages/man2/umask.2.html)、[rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)、[fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html)：核对属性、权限和同步保证，不只看函数名字。
- [GNU Coreutils Manual](https://www.gnu.org/software/coreutils/manual/coreutils.html)：对照 ln、stat、du 的选项与默认行为；GNU 选项不能无条件搬到其他系统。

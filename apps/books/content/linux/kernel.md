# Linux 内核：执行上下文与系统调用路径

> 先修：[操作系统抽象](book:linux/os)。目标：把系统调用、异常、中断、等待与调度连接起来，理解内核中的“可睡眠”约束，并能围绕一个问题阅读内核源码，而不是从第一行开始浏览。以下路径是概念模型，具体函数名与实现随内核和架构变化。

## 内核不是只有调度器

Linux 内核包含进程与调度、虚拟内存、虚拟文件系统、网络协议栈、设备驱动、安全机制等子系统。Linux 通常归为支持模块的宏内核：大量服务与驱动在内核权限范围内协作，不是每个驱动天然拥有独立进程级隔离。

可加载模块能在运行时扩展内核，但“可动态加载”不等于“出错只影响模块自己”。这里不要求加载、卸载或编写内核模块；先在用户态形成可解释的观察，再选择需要阅读的内核边界。

## 一次 read 的逻辑路径

### 入口：系统调用号与参数

用户程序经库封装或直接系统调用约定传递编号和参数。架构入口保存必要状态，进入受控权限；内核再定位相应处理路径。参数包括文件描述符、用户缓冲区地址、请求长度等，它们都不能因为来自“本机程序”而无条件信任。

文件描述符是当前进程表中的索引。内核需要找到引用的对象并检查其类型与操作能力。同一个 read 接口可能面对普通文件、管道、终端或套接字，随后分派到不同实现。“一切皆文件”在这里提供统一接口风格，不意味着实现完全相同。

### 数据路径：命中、等待和部分完成

普通文件读取可能从页缓存得到数据；管道可能等待写者；套接字可能等待网络数据。返回的字节数小于请求量不一定是错误，调用者必须按对象和协议解释短读。返回 0 对普通文件通常表示到达文件末尾，对其他对象也要按接口语义判断。

错误码是具体原因的接口，不是所有错误都应盲目重试。无效描述符、用户地址错误、可中断等待被打断、非阻塞操作暂不可完成，分别需要不同处理。某些库调用还会自动重试，观察应用层结果时要注意封装行为。

### 用户地址不能直接视为可信内核地址

内核访问用户缓冲区要使用相应机制处理访问限制和故障。用户页可能尚未驻留，用户线程也可能并发改变映射或数据。检查过一次地址，不等于之后任意读取都不受变化影响。涉及复杂结构时还要考虑复制、长度验证以及“检查的内容”和“使用的内容”是否一致。

## 上下文决定能做什么

同一段内核功能处于不同上下文时，可用操作不同。

| 上下文 | 与用户任务关系 | 典型约束 |
|---|---|---|
| 进程上下文 | 常由当前任务调用或由内核线程执行 | 在满足条件时可以阻塞等待 |
| 硬中断上下文 | 响应中断，不是普通可睡眠任务调用 | 不能任意执行可能睡眠的操作 |
| 延后处理 | 软中断、工作队列等机制各异 | 不同机制的可睡眠性不能混同 |

“进程上下文可以睡眠”也不是无条件规则。如果持有自旋锁、处于不允许调度的区域或有其他原子上下文约束，就不能调用可能阻塞的操作。工作队列通常在线程上下文中执行，但具体工作仍需满足其调用环境和锁约束。

### 为什么不能拿着自旋锁等待磁盘？

自旋锁的等待者不断检查锁状态，适合特定短临界区。若持有者发起长期阻塞，它可能长时间无法释放锁，其他 CPU 继续空转；在某些上下文下还会违反调度规则或死锁。正确选择要同时考虑临界区长度、是否可能睡眠、调用上下文与锁竞争，而非只根据“自旋锁看起来更快”。

## 等待队列：唤醒不是传送执行权

一个任务发现条件不满足，需要在正确同步下登记等待，并让出执行机会。生产者改变条件后唤醒等待者，等待者通常只是变为可运行，还要等待调度。

丢失唤醒是关键风险：若消费者先检查空队列，生产者随后放入数据并发出通知，消费者再无条件睡下，就可能睡过已经发生的事件。因此登记、条件检查和状态转换必须由正确的等待协议配合，不能手工拼几条看似顺序合理的语句。

这一原则也对应用户态条件变量：等待者重新获得锁后需要重新检查谓词，不能把一次通知当成永久有效的事实。线程章将给出具体时序。

## 例题：把一次请求的延迟分层

给定一个教学请求，用户态准备 0.1 毫秒，入口和检查 0.05 毫秒，设备相关等待 4 毫秒，唤醒后等 CPU 0.8 毫秒，返回及用户态处理 0.15 毫秒，则：

$$
T=0.1+0.05+4+0.8+0.15=5.1\ \mathrm{ms}.
$$

把入口与检查开销减半，只减少 0.025 毫秒，约为总时间的 0.49%。若只看到发生了很多系统调用，就把全部优化精力放在入口指令上，可能错过主要等待。

现实中，各阶段如何计时需要明确工具口径。一份系统调用耗时记录可能包含等待与被抢占时间，不等于这段时间都在 CPU 上执行内核代码。事件追踪也会引入开销。

## 带问题阅读源码

选择“阻塞管道读何时醒来”这样的具体问题，而不是“读懂 Linux 全部源码”。先确认本机或目标版本与架构，再查接口文档，识别入口、对象操作、等待条件及唤醒来源。

阅读时维护四张小表：对象由谁分配和释放，哪把锁保护哪些字段，哪些路径允许睡眠，错误分支怎样释放已取得的资源。找到一个函数并不等于理解它，调用者对状态的保证往往比函数体本身更关键。

可以从已审阅的本地源码静态搜索符号开始；不需要为了学机制在真实服务器上启用追踪或修改内核参数。strace 等工具可帮助观察自己启动的小程序，但输出可能包含路径和敏感参数，不能不加选择地分享。

## 练习与解题提示

1. 系统调用返回的持续时间能否全部算作内核 CPU 时间？
2. 为什么普通文件、管道和套接字都能 read，却不能套用同一等待模型？
3. 某任务被唤醒后仍延迟很久，有哪些下一步证据？
4. 在可睡眠的上下文里取得自旋锁后，是否仍能随意阻塞？
5. 例题若把设备等待从 4 毫秒降至 2 毫秒，总时间变为多少？

**答案：** 1. 不能，可能包含 I/O、调度等待和抢占。2. 统一入口会分派到不同对象操作，数据来源和协议不同。3. 看运行队列、允许用核数、节流及高优先级任务，不能继续只看设备。4. 不能，还受锁与原子上下文约束。5. 3.1 毫秒；其他阶段不变是模型假设。

## 小结与参考

内核路径由对象关系、上下文和同步约束共同决定。把入口、数据可用、唤醒和真正执行分开，才能解释为什么“请求发出了”与“程序拿到结果了”相隔很远。

- [Linux Kernel Documentation](https://docs.kernel.org/)：按目标版本阅读核心 API、锁、调度和驱动文档。
- [Kernel locking](https://docs.kernel.org/locking/index.html)：核对不同锁与上下文条件。
- [read(2)](https://man7.org/linux/man-pages/man2/read.2.html)、[syscalls(2)](https://man7.org/linux/man-pages/man2/syscalls.2.html)：先明确接口，再追踪实现。
- [Linux 源码](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/)：固定版本阅读，不把最新分支函数位置当永久契约。

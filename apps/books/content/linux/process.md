# 系统、进程与执行边界

> 先修：能打开终端，不要求学过操作系统。环境：Linux、Bash 5、GNU 用户工具；观察进程时使用 procps。所有操作限于自己创建的任务，不需要 sudo。目标：沿一条命令说明执行链，预测父子进程的状态变化，区分进程退出、任务成功和服务就绪。

## 1.1 第一个问题：到底是谁执行了命令？

打开终端，输入 `printf 'hello\n'`。眼前至少存在四种职责：终端模拟器把键盘操作转换成字符并显示输出；Shell 解释输入；正在执行的程序处理数据；内核分配处理器时间、内存和设备访问权。窗口不是 Shell，Shell 也不是内核。更换终端配色不会更换命令解释器，换成 zsh 也不会更换 Linux 内核。

Linux 严格说是内核；发行版把内核、运行库、工具、启动组件和软件包管理组合起来。服务器没有桌面环境，仍然可以通过 SSH 使用 Shell。SSH 的作用是建立远程通信与身份认证通道，不是让你的本地 Shell 直接变成远端的内核。

![图 1-1：终端、Shell、用户进程与内核的职责边界。图中箭头表示请求关系，不代表四台机器，也不代表每条命令都会创建外部进程。](asset:linux-process)

本例还有一个容易忽略的细节：`printf` 在 Bash 中通常是内建命令。可以用 `type -a printf` 查看命令解析结果。内建命令可以直接在 Shell 执行上下文中工作，而外部程序需要执行文件。不要只根据命令名字就断言“Shell 为它 fork 了一个进程”。

系统调用是用户程序请求内核服务的受控入口。例如 `read()`、`write()`、`openat()` 请求读写或打开对象。内核会检查地址、权限和对象状态；程序不能把任意字符串当成可访问的内核地址。库函数与系统调用也不是一一对应：一次格式化输出可以先进入用户态缓冲，多次输出合并后才调用 `write()`。反过来，一次库函数操作也可能调用多个系统接口。

## 1.2 进程携带什么，线程又共享什么？

**程序文件**是静态的代码与数据，**进程**是一次执行的资源与身份集合，**线程**是可被调度的执行流。一个程序文件可以被执行多次；一个进程可以包含多个线程。

| 对象或属性 | 用途 | 关键边界 |
|---|---|---|
| PID 与父 PID | 标识当前 PID 命名空间中的进程及父子关系 | PID 会复用，容器内外看到的编号也可能不同 |
| 虚拟地址空间 | 组织代码、栈、堆和映射文件 | 相同虚拟地址不代表相同物理内存 |
| 文件描述符表 | 引用已经打开的文件、管道、套接字 | 小整数只在本进程的表中有意义 |
| 工作目录 | 解析相对路径的起点 | 改变子进程目录不改变父进程目录 |
| 环境变量 | 向新程序传递字符串配置 | 不等于 Shell 的全部变量，也不是双向通信 |
| 安全身份与资源边界 | 决定访问权和可用资源 | 不仅是用户名，还可能受 ACL、cgroup 等约束 |

同一进程的线程通常共享地址空间、工作目录和文件描述符表，但各自保有寄存器、栈以及调度状态。在 Linux 中，调度实体通常是线程；“一个进程占两核”实际意味着它的多个线程可能同时在不同逻辑 CPU 上执行。线程共享资源不意味着访问天然安全，数据竞争与同步将在[线程、同步与并发正确性](book:linux/threads)中展开。

可以把进程想成一张装有资源引用的工作台，而不是装满全部数据的独立箱子。共享库页面、映射文件、打开文件描述等对象可能被多个进程共同引用。理解这种“各自的表，共享的对象”关系，是下一章区分文件描述符与 inode 的基础。

## 1.3 一次外部程序启动：fork、exec、wait

传统 Unix 模型可分成三个动作，名称相似却不可互换。

1. **`fork()` 创建子进程。** 父子进程从同一逻辑执行位置继续，但返回值不同。父进程得到子 PID，子进程得到 0；失败时父进程得到 -1，不会多出一个成功创建的子进程。
2. **`execve()` 替换程序映像。** 成功后不返回原来的调用位置。进程仍然是这个进程，PID 不因成功 exec 而另行分配；代码、栈等执行内容被新程序替换。工作目录等部分属性保留，标记为 close-on-exec 的描述符会关闭。
3. **`wait()` 或 `waitpid()` 回收退出信息。** 子进程退出后，父进程取得退出原因与状态，内核才能释放用于报告退出的记录。

Linux 的 fork 通常使用写时复制。初始时，父子可以映射相同的数据页；其中一方尝试写入时，再按需要分配私有页。这是实现效率机制，不是让普通父子进程自动共享可互相修改的所有变量。`exec` 也不是“在原进程里面再启动一个永久嵌套的进程”。

![图 1-2：父进程 fork 后继续自己的路径；子进程 exec 替换映像，退出后等待父进程回收。父进程是否阻塞取决于 wait 的使用方式。](asset:linux-lifecycle)

Shell 还可能使用 `posix_spawn()` 一类接口、不同的创建实现或避免不必要的进程。这幅图用于理解语义，不能替代对某个 Shell 版本的实现追踪。

### 动手：让 Bash 明确报告子任务的结果

下面只有一个自己创建的子任务，没有向其他 PID 发送信号。

```bash
# example: process-child
bash -c 'printf "child output\n"; exit 7' &
pid=$!
if wait "$pid"; then
  rc=0
else
  rc=$?
fi
printf 'collected exit=%s\n' "$rc"
```

预期先看到 `child output`，随后看到 `collected exit=7`。`$!` 取得刚启动的后台任务 PID，`wait` 取得结果。这里故意返回 7，说明“进程正常执行了 exit”与“约定的业务成功”不是同一句话。

`$?` 总是关联刚完成的命令，不能隔着一条 `printf` 再去取原错误码。代码在 `else` 中立即保存状态；如果把判断写成 `if ! wait ...`，进入分支后的 `$?` 是逻辑取反后的结果，不能照搬上述写法。管道会进一步改变状态的解释，见[Shell 数据流](book:linux/shell)。

## 1.4 环境与工作目录：继承不是远程控制

变量可以存在于 Shell 内部，却没有被导出给外部程序。`export` 把变量加入以后启动程序可获得的环境。子进程取得的是启动时构造的环境内容；之后修改子进程环境，不会沿着父子关系回写父进程。

```bash
# example: process-environment
(
  COURSE_STATE=parent
  export COURSE_STATE
  bash -c 'COURSE_STATE=child; printf "child=%s\n" "$COURSE_STATE"'
  printf 'parent=%s\n' "$COURSE_STATE"
)
```

预期是 `child=child` 和 `parent=parent`。最外层圆括号让练习发生在子 Shell 环境中，结束后不把演示变量留在当前交互 Shell。注意 `source script.sh` 不等于 `bash script.sh`：前者在当前 Shell 上下文执行文件，因此文件里的 `cd`、变量赋值和 `exit` 可能直接影响当前会话。不要 source 尚未审阅的脚本。

### 例题：为什么 `cd` 需要内建实现？

设父 Shell 当前目录是 `/home/student`，它启动一个子程序，子程序执行 `chdir("/tmp")`。修改的是子进程的工作目录字段；父 Shell 下一次解析相对路径时，仍从 `/home/student` 出发。要让交互 Shell 自身改变目录，必须改变这个 Shell 的状态，所以 `cd` 通常由内建命令实现。

由此还能预测两个结果：`(cd /tmp; pwd)` 只临时改变子 Shell 环境；在支持的上下文里，花括号命令组 `{ ...; }` 通常不因分组本身创建子 Shell。不要用“带括号的都一样”来记语法。

## 1.5 状态机：运行、等待、停止与退出

进程状态描述的是某一时刻的调度或退出情况，不是应用的健康评分。观察工具拿到的是快照；一个任务在两次采样之间可能经历很多次状态转换。

| 常见标记 | 含义 | 下一步应该问什么 |
|---|---|---|
| R | 正在运行或可运行、等待 CPU | 允许使用多少 CPU，是否在排队？ |
| S | 可中断睡眠，等待事件 | 是正常等输入，还是等不到预期事件？ |
| D | 不可中断等待，常涉及内核 I/O | 等待的资源是什么，有没有持续性证据？ |
| T / t | 停止或被跟踪 | 是否被作业控制或调试器停止？ |
| Z | 已退出，父进程尚未回收 | 为什么父进程还没有处理退出记录？ |

用 `sleep 5 &` 启动自己的等待任务，立即记录 `$!`，再用 `ps -o pid,ppid,stat,etime,time,comm -p "$pid"` 观察，最后 `wait "$pid"`。它通常处于 S，但任务很短或机器调度不同可能让快照错过它。不要把“示例预期状态”写成每次都必须出现的断言。

**僵尸**已经不执行用户代码，因此对它反复发送 SIGKILL 不能让它“再死一次”。**孤儿进程**则是父进程已经退出、自己可能仍在运行的进程；它会被相应的 reaper 接管，具体可能涉及 PID 命名空间中的 init 或子进程回收器。孤儿与僵尸不是同义词。

D 状态也不表示进程永远无法退出。信号可能先挂起，等相关内核等待返回后才被处理。此时盲目重复 kill 不会修好阻塞的存储或设备路径。

## 1.6 时间模型：慢在哪里，忙了几核？

设墙钟时间为 $T_w$，累计用户态 CPU 时间为 $T_u$，累计内核态 CPU 时间为 $T_s$。在统计口径明确、计入同一组线程或子任务的前提下，平均占用逻辑 CPU 数为：

$$
\bar c=\frac{T_u+T_s}{T_w}.
$$

对单条不能并行重叠的执行路径，可以把墙钟时间概念性拆为运行、等待 CPU 与其他等待：

$$
T_w=T_{\mathrm{run}}+T_{\mathrm{ready}}+T_{\mathrm{wait}}.
$$

第二式不能直接拿所有线程的累计 CPU 时间代入第一项。多线程在时间轴上重叠，累计的 25 秒 CPU 时间完全可能发生在 10 秒墙钟内。

### 例题：总 CPU 时间足够，为什么还有等待？

某任务墙钟 10 秒，用户态 23 秒，内核态 2 秒，所以平均占用 2.5 个逻辑 CPU。如果任务所在资源范围最多允许 4 个 CPU，同时假设没有额外配额限制，则相对这个 4-CPU 上限的平均占用比例为 $2.5/4=62.5\%$。这不表示剩余的 37.5% 都能通过加线程消除：可能存在串行部分、同步、数据依赖与 I/O。

另一个任务墙钟 10 秒，累计 CPU 只有 0.2 秒，只能推出平均用核约 0.02，不能单凭它断言磁盘慢。网络等待、锁等待、主动 sleep、CPU 配额节流都需要不同证据。可靠诊断见[系统观察](book:linux/observe)。

Bash 的 `time` 关键字和外部 `/usr/bin/time` 在语法、格式和统计对象上可能不同；给 Shell 管道计时与给其中一个外部程序计时也不是同一范围。报告结果时要把命令与统计范围写在一起。

## 1.7 终端、进程组与信号

交互式 Shell 的作业控制把相关进程组织为作业，一个管道里的多个进程通常属于同一个进程组。终端维护一个前台进程组；在常见终端设置下，`Ctrl+C` 触发 SIGINT，发送给前台进程组，而不是根据屏幕上最后显示的 PID 选择单个进程。

`Ctrl+Z` 通常触发 SIGTSTP，暂停前台作业。`jobs` 使用 Shell 的作业号，`ps` 显示系统进程号，两种编号不要混用。`fg` 恢复前台作业，`bg` 请求其在后台继续；后台任务若尝试读取控制终端，还可能收到 SIGTTIN 而停止。

SIGTERM 的默认动作通常是终止，但程序可以安装处理逻辑，以便关闭资源或保存必要状态。SIGKILL 与 SIGSTOP 不能被捕获、阻塞或忽略。这里的“不能捕获”不代表发出 SIGKILL 就保证数据已经落盘，也不代表所有内核等待立刻结束。

对自己管理的任务，先使用应用自己的退出方式或所属服务管理器；只有确认对象后才发送合适的信号。PID 会复用，昨天记下的编号不能作为今天终止进程的可靠身份。不要在共享机器上用广泛的进程名匹配替代任务所有权检查。

## 1.8 后台、脱离终端与持久服务

在命令后加 `&`，主要改变 Shell 等待方式和作业控制安排，不会自动赋予自动重启、日志轮换、身份隔离或开机启动能力。

| 需求 | 合适的职责工具 | 仍需负责的事情 |
|---|---|---|
| 暂时并行运行几条命令 | Shell 后台作业与 wait | 保存 PID、收集结果、限制并发 |
| 断开连接后再接回交互会话 | tmux 等终端复用器 | 检查任务输出和资源消耗 |
| 长期运行服务 | systemd 等服务管理器 | 就绪检查、重启策略、权限与日志 |
| 共享计算集群中的批处理 | 集群调度器 | 使用已分配资源、验证作业产物 |

`nohup` 主要调整 SIGHUP 相关行为并按条件安排输出；它不是服务管理器。SSH 断开后的具体行为受 Shell、终端、信号处理和管理方式影响，不能用“加了 & 就绝对不结束”或“关窗口必定杀死任务”概括。

启动命令返回 0，只说明约定中的启动动作成功。服务可能尚未监听端口，也可能监听后才发现配置无效。完整链路是“管理器接受请求 → 进程存在 → 服务就绪 → 业务请求正确”，详见[服务生命周期](book:servers/services)。

## 1.9 综合任务：写一份子任务执行报告

在自己创建的临时目录中完成三个小任务：一个 `exit 0`，一个 `exit 7`，一个等待一秒后退出。不要引入无限循环、系统服务或陌生 PID。

报告至少记录任务名称、启动方式、退出状态和预期输出。启动后能用 `ps` 看见它，只是中途观察；最终必须由 `wait` 收集状态，并检查输出内容是否符合约定。短任务可能在 ps 前退出，这不是观察工具失败，更不是任务没有运行。

进一步思考：若第二个任务失败，第一个任务的输出是否仍有效？是否要继续第三个任务？这属于调用者的工作流设计，不是内核会自动替你决定的事情。

## 练习与解题提示

**基础层**

1. `execve()` 成功后 PID 是否必须改变？旧程序的下一条语句是否继续执行？
2. 子进程修改环境变量和工作目录，父进程是否自动同步？`source` 为什么可能不同？
3. 一个四线程进程墙钟 8 秒、累计 CPU 12 秒，平均占几核？能说每线程都运行了 3 秒吗？

**机制层**

4. `ps` 显示 Z，你应重点检查谁？为什么重复 kill 通常没有帮助？
5. 父进程先退出，子进程仍在运行，这一定是僵尸吗？
6. 一个管道接收 Ctrl+C，为什么可能有不止一个进程结束？

**工程层**

7. 构建任务已经退出且状态为 0，但预期文件不存在。应判定任务交付成功吗？还缺什么契约？
8. 程序用核 2.5，机器有 16 核，但它只允许使用 4 核。报告一个没有分母说明的“CPU 15.6%”有什么问题？

**解题提示与答案**

1. PID 不因成功 exec 而改变，旧映像被替换，不继续旧语句；失败时才返回错误给旧程序。2. 不自动同步；source 在当前 Shell 执行，能修改当前上下文。3. 平均 1.5 核，总量不能给出各线程分配。

4. 重点检查父进程是否正确 wait，以及其管理方式；僵尸已经退出。5. 不是，孤儿描述父子关系，僵尸描述已退出未回收。6. 终端通常向整个前台进程组发送 SIGINT。

7. 不能。除了退出码，还要约定产物位置、完整性和内容条件；也可能是程序本身错误地报告成功。8. 使用全机 16 核作分母会掩盖应用实际的 4 核边界；应同时说明平均用核数和配额。

## 小结与参考

理解执行边界，可以把“敲了一条命令”拆成命令解析、资源继承、程序替换、调度等待、退出回收和业务验收。排查时先认清对象，再选择工具；任何单一 PID、状态字符或退出码，都不能代替完整的任务契约。

- Linux man-pages：[fork(2)](https://man7.org/linux/man-pages/man2/fork.2.html)、[execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html)、[wait(2)](https://man7.org/linux/man-pages/man2/wait.2.html)。重点核对返回值、保留属性及回收条件，不必第一次就记住全部标志。
- [signal(7)](https://man7.org/linux/man-pages/man7/signal.7.html)：核对信号默认动作、不可捕获信号与线程相关细节。
- [Operating Systems: Three Easy Pieces](https://pages.cs.wisc.edu/~remzi/OSTEP/)：依次读 Process、Process API 与 CPU Scheduling，将 API 与调度模型相连。
- [鸟哥的 Linux 私房菜](https://linux.vbird.org/)：配合进程管理与 Bash 章节练习交互工具；截图和具体发行版输出可能与本机不同。

**操作验证边界：** 本章可移植的 Bash 小例子与 Linux 内核行为分开检查。能在 Windows 的 Git Bash 中运行变量和 wait 示例，不等于验证了 Linux PID 命名空间、D 状态或终端断连行为。

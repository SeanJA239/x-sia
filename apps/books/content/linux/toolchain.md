# 从目标文件到运行：链接、ABI 与装载

> 先修：编译前端、虚拟内存与进程。目标：区分编译、汇编、链接和装载，解释符号、重定位与调用约定，并沿一个双文件程序定位构建错误。示例只生成本地小程序，不需要管理员权限。

## 为什么编译完还不能直接运行？

单独编译一个源文件时，编译器可能不知道另一个文件中函数的最终位置。目标文件需要记录已生成代码、数据、符号定义、未解决引用和重定位信息，让后续链接器组合。

汇编器把汇编表示转换为机器码及目标文件记录；链接器安排各输入部分、解析符号并处理相应重定位；装载器再根据可执行文件的运行视图建立映射，准备程序启动。某些构建命令把这些步骤串起来，但职责并未因此消失。

## 双文件例子：声明与定义

在自己新建的练习目录中保存三个文件。

```c
/* add.h */
#ifndef COURSE_ADD_H
#define COURSE_ADD_H
int add(int left, int right);
#endif
```

```c
/* add.c */
#include "add.h"
int add(int left, int right) { return left + right; }
```

```c
/* main.c */
#include <stdio.h>
#include "add.h"
int main(void) {
    printf("%d\n", add(2, 3));
    return 0;
}
```

用已有 C 编译器运行：

```bash
cc -std=c17 -Wall -Wextra -Wpedantic -c add.c -o add.o
cc -std=c17 -Wall -Wextra -Wpedantic -c main.c -o main.o
cc main.o add.o -o demo
./demo
```

预期输出 5。前两步只编译并生成目标文件，最后链接时才把 main 对 add 的引用与定义联系起来。头文件中的声明提供编译所需的类型接口，不等于已经提供实现代码。

本例输入避免了有符号整数溢出，不承诺 add 对任意 int 输入都得到数学整数结果。运行环境的目标格式也可能不同：Linux 常用 ELF，Windows 工具链可能输出 PE/COFF，二者不能混称。

## 符号与重定位是什么？

符号把名字关联到对象中的定义、引用或属性。链接时需要处理可见性、重复定义、弱符号等规则。C++ 还可能通过名字改编编码重载等信息，C 和 C++ 的链接接口不能仅凭源文件里名字相同就保证兼容。

重定位不是“把所有地址统一加一个常数”。记录说明某处需要根据符号、附加数和位置等信息进行何种计算。不同目标架构和重定位类型有不同范围与编码要求。

### 一个 PC 相对的抽象算例

用常见解释符号记目标地址为 $S$，附加数为 $A$，重定位位置为 $P$，一种概念形式是：

$$
D=S+A-P.
$$

若 $S=0x1200,A=-4,P=0x1000$，则 $D=0x1fc$。具体机器的记录格式与“位置”的定义必须按 ABI 文档核对；此式不适用于所有重定位，也不意味着所有分支都能编码任意距离。

## ELF 的链接视图与运行视图

section 常用于链接组织，例如代码、只读数据、可写数据与符号信息。segment 描述装载器需要的运行映射，一段装载范围可能包含多个 section。因此“一个 section 就是一个运行时映射”并非通用规则。

未初始化静态存储常通过类似 `.bss` 的机制表达：运行时需要空间和零初始化，但文件中不必为每个零保存实体字节。程序文件大小与启动后的虚拟或物理内存占用不应该直接相等。

在真实 Linux ELF 环境中可用 `readelf -h/-S/-l`、`nm`、`objdump` 等已安装工具观察自己构建的文件。这里不要求对未知可执行文件运行或加载；静态查看与执行是不同权限和风险边界。

## ABI：函数名相同还不够

ABI 规定参数与返回值放在哪里、哪些寄存器由调用者或被调用者保存、栈对齐、结构体布局等二进制约定。编译器和语言运行时必须协调这些条件。

例如两个模块对结构体字段顺序或打包方式有不同理解，链接可能成功，运行却读取错误偏移。一个模块以为函数返回整数，另一个按不同类型约定提供返回值，也不能由链接器名字匹配自动修复。

跨语言接口应使用明确的稳定边界、固定可解释的数据布局和所有权协议。由谁分配、由谁释放、异常是否能跨边界传播，都属于接口，而不是注释中可有可无的补充。

## 静态链接、动态链接与装载

静态库通常是目标文件集合，链接器按规则选择需要的成员，并不必然把整个库内容全部复制到输出。库搜索顺序和链接方式会影响符号解析。

动态链接把部分解析或装载工作留到运行阶段。共享库路径、版本、符号兼容和运行时重定位都可能成为启动失败原因。构建时找到库，不代表部署机器一定能找到相同兼容库。

### main 之前发生什么？

内核根据可执行格式建立初始执行环境；动态可执行程序还可能涉及解释器/动态装载器。启动代码与运行库准备参数、环境和运行所需状态，处理适用初始化后再调用 main。main 返回也通常通过运行库退出路径处理，而不是 CPU 自动把函数返回当成机器关机。

位置无关代码与地址随机化涉及运行地址可变的问题，但随机化不是内存安全证明。是否启用、随机化范围与安全收益都受平台与配置影响。

## 按阶段定位错误

| 现象 | 先定位的边界 | 典型检查 |
|---|---|---|
| 找不到头文件、类型冲突 | 预处理与编译 | include 路径、声明和选项 |
| 未定义符号或重复定义 | 链接 | 输入目标文件、库顺序、符号可见性 |
| 程序无法装载、缺少共享库 | 运行时装载 | 目标架构、解释器、库及版本 |
| 启动后崩溃或结果错误 | 运行语义 | ABI、对象生命周期、输入和逻辑 |

不要通过不断追加随机编译选项来修复所有错误。保留实际命令、工具版本、输入文件与完整错误信息；不要把含秘密路径或凭据的完整环境变量列表当成必要日志。

## 练习与解题提示

1. 只链接 main.o 而不提供 add 的定义，预期在哪一阶段失败？
2. 声明写在头文件里，为什么不等于有函数实现？
3. `.bss` 很大是否必然使文件同样大？
4. 链接成功能否证明跨模块结构体布局一致？
5. 动态库在开发机器存在，为何部署仍可能失败？

**答案：** 1. 链接时无法解决符号，具体消息由工具链决定。2. 声明提供接口，定义提供相应实体。3. 不必，零初始化空间可以由运行映射表达。4. 不能，布局与 ABI 还要一致。5. 可能缺少库、版本不兼容、搜索路径或架构不同。

## 小结与参考

把源语言、目标格式、ABI 和装载环境连起来，才能解释“编译成功但链接失败”“链接成功但运行失败”。Linux 学习到这里，已与编译原理、体系结构和操作系统形成一条连续路径。

- [GCC overall options](https://gcc.gnu.org/onlinedocs/gcc/Overall-Options.html)：核对 -E、-S、-c 和最终链接的停止边界。
- [GNU Binutils](https://sourceware.org/binutils/docs/)：学习 nm、objdump、readelf 与链接器，不把输出格式当成跨平台常量。
- [System V ABI](https://refspecs.linuxfoundation.org/elf/gabi4+/contents.html)：理解 ELF 通用结构，再阅读目标架构的具体 ABI。
- [CS:APP](https://csapp.cs.cmu.edu/)：链接、虚拟内存与进程章节可相互对照。
